# UTF4005 — MonoBehaviour classes in test assemblies should be hidden from the Add Component menu

Detects a class deriving from `UnityEngine.MonoBehaviour` that is declared in a test assembly and is not hidden from the Unity Editor's Add Component menu with `[AddComponentMenu("/")]`. Test doubles (test stubs, test spies, and fakes) that derive from `MonoBehaviour` exist only to be attached from test code, but the Editor lists every `MonoBehaviour` in the picker, so they show up next to the production components.

| Item     | Value   |
|----------|---------|
| Category | Style   |
| Enabled  | True    |
| Severity | Warning |
| CodeFix  | False   |

Message: "'{0}' is declared in a test assembly and appears in the Add Component menu of the Unity Editor, where it can be attached to a scene object by mistake. Apply AddComponentMenu with a menu name that starts with '/' to hide it."

`{0}` is the name of the class. The diagnostic is reported at the class name.

Severity is Warning because the tests run and pass. The cost is a cluttered picker in the Editor and a test double that a developer can attach to a scene object by mistake; nothing has to be stopped before the run.

## Motivation

The Add Component button in the Inspector and the Component menu of the Editor list every class that Unity resolves as a component, whichever assembly declares it. A test assembly of any size accumulates `MonoBehaviour` subclasses written as test doubles: a spy that records pointer events, a stub that destroys itself on click, a fake used as a placeholder component. Each of them appears in the picker under "Scripts", named like a real component and indistinguishable from one, so a developer editing a scene can attach it by mistake, and a search in the picker returns test doubles among the results.

`AddComponentMenu` controls where a script appears in the Component menu, and the [AddComponentMenu constructor](https://docs.unity3d.com/ScriptReference/AddComponentMenu-ctor.html) states: "If `menuName` is "" or starts with "/" the component will be hidden from the menu". The two forms differ in the Unity versions that honor them:

- A menu name that starts with `/` hides the component on Unity 2021.1 and later. The 2021.1 Script Reference is the first to document it; the 2020.3 Script Reference documents only the empty string (verified against both).
- The empty string is documented on every version, but Unity 2023.2.0a17 through part of the 6000 series does not honor it and lists the class in the Add Component menu ([UUM-99267: Component is not hidden from Add Component Menu when using AddComponentMenu("")](https://issuetracker.unity3d.com/product/unity/issues/guid/UUM-99267)).

This rule accepts only a menu name that starts with `/` and reports the empty string: `/` hides the component on every version from 2021.1 on, while `""` fails on the versions affected by UUM-99267. A project on Unity 2020 or earlier, where only `""` is documented, should disable the rule.

Unity has no notion of a test assembly that an analyzer can read from the compilation. A test assembly is one created with "Create Test Assembly Folder" or by hand with the "Test Assemblies" option of the assembly definition, and neither leaves a mark in the compiled code beyond a reference to `nunit.framework` and `UnityEngine.TestRunner`. A reference to those assemblies is not a usable criterion: a runtime library of test helpers references them and is not a test assembly. This rule follows the two naming conventions of the [Package layout](https://docs.unity3d.com/Manual/cus-layout.html) page instead, which places tests under `Tests/Editor/` and `Tests/Runtime/` in assemblies named `<package-name>.Editor.Tests` and `<package-name>.Tests`, and treats an assembly as a test assembly when either holds:

- The assembly name ends with `.Tests`.
- The path of the source file contains a directory named `Tests`. This also matches the `Tests` folder that "Create Test Assembly Folder" creates under `Assets/`.

### Why existing analyzers cannot be used instead

NUnit.Analyzers has no rule about `MonoBehaviour` or `AddComponentMenu`. Verified with NUnit.Analyzers 3.9.0.

## Bad

```csharp
// Assets/Tests/Runtime/TestDoubles/SpyButtonClickReceiver.cs, assembly MyGame.Tests
using UnityEngine;
using UnityEngine.UI;

public class SpyButtonClickReceiver : MonoBehaviour   // UTF4005; listed in the Add Component menu as "Spy Button Click Receiver"
{
    public int ClickCount { get; private set; }

    private void Awake()
    {
        GetComponent<Button>().onClick.AddListener(() => ClickCount++);
    }
}
```

```csharp
// Assets/Tests/Runtime/TestDoubles/StubDestroyingItselfWhenPointerDown.cs, assembly MyGame.Tests
using UnityEngine;
using UnityEngine.EventSystems;

[AddComponentMenu("")]   // UTF4005; not honored on Unity 2023.2.0a17 through part of the 6000 series (UUM-99267)
public class StubDestroyingItselfWhenPointerDown : MonoBehaviour, IPointerDownHandler
{
    public void OnPointerDown(PointerEventData eventData)
    {
        Destroy(gameObject);
    }
}
```

```csharp
// Assets/Tests/Runtime/TestDoubles/FakeComponent.cs, assembly MyGame.Tests
using UnityEngine;

[AddComponentMenu("Test Doubles/Fake Component")]   // UTF4005; a visible menu path
public class FakeComponent : MonoBehaviour
{
}
```

## Good

```csharp
// Assets/Tests/Runtime/TestDoubles/SpyButtonClickReceiver.cs, assembly MyGame.Tests
using UnityEngine;
using UnityEngine.UI;

[AddComponentMenu("/")]   // Hidden from the Add Component menu
public class SpyButtonClickReceiver : MonoBehaviour
{
    public int ClickCount { get; private set; }

    private void Awake()
    {
        GetComponent<Button>().onClick.AddListener(() => ClickCount++);
    }
}
```

```csharp
// Assets/Tests/Runtime/SpyBase.cs, assembly MyGame.Tests
using UnityEngine;

public abstract class SpyBase : MonoBehaviour   // Not reported; an abstract class cannot be attached
{
}
```

```csharp
// Assets/Tests/Runtime/ButtonTest.cs, assembly MyGame.Tests
using NUnit.Framework;
using UnityEngine;

public class ButtonTest
{
    private class StubComponent : MonoBehaviour   // Not reported; a nested class is never resolved as a component
    {
    }

    [Test]
    public void AttachStub()
    {
        var stub = new GameObject().AddComponent<StubComponent>();
        Assert.That(stub, Is.Not.Null);
    }
}
```

```csharp
// Assets/Scripts/Runtime/Player.cs, assembly MyGame
using UnityEngine;

public class Player : MonoBehaviour   // Not reported; neither the assembly name nor the path marks a test assembly
{
}
```

## Notes

- The rule inspects every non-abstract, non-generic, top-level class declaration in the compilation that derives from `UnityEngine.MonoBehaviour` at any depth, and reports the class when the compilation is a test assembly and the class declaration itself has no `[AddComponentMenu]` whose menu name starts with `/`. An `[AddComponentMenu]` applied to a base class is not looked at; each concrete subclass needs its own. Any other menu name, including the empty string, is reported. A deliberately visible test component is suppressed at the class with `#pragma warning disable UTF4005`.
- A compilation is a test assembly when its assembly name ends with `.Tests`, or when the file path of the syntax tree that declares the class contains a `Tests` directory segment. The segment is matched case-sensitively, between `/` or `\` separators, so `Assets/Tests/Foo.cs`, `Packages/com.example.foo/Tests/Runtime/Foo.cs`, and `Library\PackageCache\com.example.foo@1.0.0\Tests\Editor\Foo.cs` all match, while `Assets/TestsOfFoo/Foo.cs` and `Assets/tests/Foo.cs` do not. An assembly named `Tests` with no `.` prefix is matched by its path only. A test assembly that follows neither convention is not recognized; add `.Tests` to the assembly name or move it under a `Tests` folder.
- Abstract classes, generic classes, and nested classes are not reported: an abstract class cannot be instantiated, the picker has no way to supply type arguments to a generic class, and Unity resolves the component class of a script from its top-level classes only.
- Unity selects the class whose name matches the file name when a file declares several classes (see [Naming scripts](https://docs.unity3d.com/Manual/naming-scripts.html)), so a class declaration is reported only when it is the only top-level type declaration in its file (classes, structs, interfaces, enums, and delegates all count) or when the class name equals the file name without extension, compared ordinally. A `MonoBehaviour` sharing a file with other types under a name that matches none of them is not resolved as a component and is not reported.
- For a partial class, `[AddComponentMenu]` is looked up across all declarations, and the file-name test above is applied to each declaration on its own; the diagnostic is reported at the declaration that passes it, or not at all when none does, since only the file named after a partial class can be used as a component.
- The menu name is read from the first constructor argument of `[AddComponentMenu]` when it is a constant string. A non-constant argument is treated as visible and reported.
- `ScriptableObject` subclasses, editor windows, and other classes that do not derive from `MonoBehaviour` are not listed in the Add Component menu and are not inspected.
- The rule does nothing in a compilation where `UnityEngine.MonoBehaviour` cannot be resolved.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF4005.severity = suggestion
```

On Unity 2020 or earlier, where a menu name that starts with `/` is not documented to hide the component, disable the rule instead:

```editorconfig
dotnet_diagnostic.UTF4005.severity = none
```
