# UTF2001 — Assert.ThrowsAsync, CatchAsync, and DoesNotThrowAsync are not supported

Detects any call to `Assert.ThrowsAsync`, `Assert.ThrowsAsync<TActual>`, `Assert.CatchAsync`, `Assert.CatchAsync<TActual>`, or `Assert.DoesNotThrowAsync`. These methods wait for the returned `Task` synchronously on the calling thread. Unity Test Framework runs tests on the main thread, so the Editor freezes.

| Item     | Value     |
|----------|-----------|
| Category | Assertion |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported. Test the exception with try/catch in an 'async Task' test method instead."

`{0}` is the called method with its class, e.g. `Assert.ThrowsAsync`, `Assert.CatchAsync`, or `Assert.DoesNotThrowAsync`. Generic overloads are reported with the same name.

The diagnostic is reported at the invocation.

Severity is Error because running the test can freeze the Editor: the returned `Task` is waited on synchronously on the main thread, so any continuation that must run on the main thread never gets scheduled. At Warning or below, the test would be run and the Editor would have to be killed.

## Motivation

The official documentation ([Async tests](https://docs.unity3d.com/Manual/test-framework/reference-async-tests.html)) states: "NUnit's assertion for asynchronous code, `Assert.ThrowsAsync`, blocks the calling thread until the async function completes", and that because Unity runs async functions on the main thread by default, this can cause the Editor to freeze. It recommends wrapping the awaited code in try/catch instead.

In the NUnit build bundled with Unity (`com.unity.ext.nunit`, based on NUnit 3.5), `Assert.ThrowsAsync(IResolveConstraint, AsyncTestDelegate)` creates an `AsyncInvocationRegion`, invokes the delegate, and calls `WaitForPendingOperationsToComplete`, which calls `Task.Wait()` on the calling thread. `Assert.CatchAsync` delegates to `Assert.ThrowsAsync` with an `InstanceOfTypeConstraint`. `Assert.DoesNotThrowAsync` calls `Assert.That(code, new ThrowsNothingConstraint())`; an `AsyncTestDelegate` converts to neither `TestDelegate` nor `ActualValueDelegate<TActual>`, so the `Assert.That(object, IResolveConstraint)` overload is chosen and `ExceptionInterceptor.Intercept` waits on the returned task the same way.

In Unity that calling thread is the main thread, and async continuations are posted to `UnitySynchronizationContext`, which is pumped by the main thread. The wait blocks the pump, the continuation never runs, and the Editor freezes. `await Task.Yield()`, `await Task.Delay(...)`, `await Awaitable.NextFrameAsync()`, and awaiting any Unity API are enough to trigger it. This is the same mechanism described in UTF1002 and UTF1004.

Every argument to these methods is an `AsyncTestDelegate`, so there is no safe way to call them; the rule reports every invocation. Whether a given `Task` actually deadlocks depends on its awaits: a task whose continuations all run off the main thread (for example, with `ConfigureAwait(false)` everywhere) completes, but it still stalls the whole test run for its duration, and the analyzer cannot tell the two apart.

Passing an async delegate to `Assert.That` with a `Throws` constraint, or to `Assert.Throws`, `Assert.Catch`, or `Assert.DoesNotThrow`, is covered by UTF2002.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers treats `Assert.ThrowsAsync` as the correct API for asynchronous code, because on a regular .NET test host `Task.Wait()` merely blocks a worker thread. No rule reports a call to it. Verified with NUnit.Analyzers 3.9.0; the one rule that inspects the delegate argument of exception assertions there (NUnit2044, DelegateRequired) reports passing a `Task` instead of a delegate, which is a different defect.

## Bad

```csharp
using System;
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public void ThrowsAsyncFreezes()
    {
        Assert.ThrowsAsync<InvalidOperationException>(async () => await FooAsync());   // UTF2001; freezes the Editor
    }

    [Test]
    public void CatchAsyncFreezes()
    {
        Assert.CatchAsync(() => FooAsync());   // UTF2001; reported regardless of the delegate's shape
    }

    [Test]
    public void DoesNotThrowAsyncFreezes()
    {
        Assert.DoesNotThrowAsync(BarAsync);   // UTF2001
    }

    private static async Task FooAsync()
    {
        await Task.Yield();
        throw new InvalidOperationException("boom");
    }

    private static async Task BarAsync()
    {
        await Task.Yield();
    }
}
```

## Good

```csharp
using System;
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public async Task ExceptionIsThrown()
    {
        try
        {
            await FooAsync();
        }
        catch (InvalidOperationException e)
        {
            Assert.That(e.Message, Does.Contain("boom"));
            return;
        }

        Assert.Fail("Expected InvalidOperationException was not thrown");
    }

    [Test]
    public async Task ExceptionIsNotThrown()
    {
        await BarAsync();   // an unexpected exception fails the test by itself
    }

    private static async Task FooAsync()
    {
        await Task.Yield();
        throw new InvalidOperationException("boom");
    }

    private static async Task BarAsync()
    {
        await Task.Yield();
    }
}
```

## Notes

- Every overload of `Assert.ThrowsAsync`, `Assert.CatchAsync`, and `Assert.DoesNotThrowAsync` is reported, including the generic `ThrowsAsync<TActual>` and `CatchAsync<TActual>` and the overloads taking a `Type` or an `IResolveConstraint`.
- Only methods declared on `NUnit.Framework.Assert` are matched. A wrapper in user code that forwards to them is not detected.
- `ConfigureAwait(false)` inside the delegate does not exempt the call; the rule does not inspect the delegate.
- Do not write `try { await FooAsync(); Assert.Fail(); } catch (Exception e) { ... }` with a catch-all: it swallows the `AssertionException` thrown by `Assert.Fail`. Catch the expected exception type, or set a flag inside the catch and assert it after the block, as the official documentation shows.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF2001.severity = warning
```
