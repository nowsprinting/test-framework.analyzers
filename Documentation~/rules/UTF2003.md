# UTF2003 — Async delegates are not supported as the actual value of the constraint model

Detects an async delegate passed as the actual value of `Assert.That` with a constraint that is not a `Throws` constraint (`Assert.That(async () => await GetAsync(), Is.EqualTo(1))`), or passed as the actual value of `Assume.That` with any constraint. NUnit evaluates the delegate and waits for the returned `Task` synchronously on the calling thread. Unity Test Framework runs tests on the main thread, so the Editor freezes.

| Item     | Value     |
|----------|-----------|
| Category | Assertion |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "Async delegates are not supported as the actual value of '{0}'. Await the operation in an async test method and assert on its result instead."

`{0}` is the method that receives the delegate: `Assert.That` or `Assume.That`.

The diagnostic is reported at the delegate argument.

Severity is Error because running the test can freeze the Editor: the returned `Task` is waited on synchronously on the main thread, so any continuation that must run on the main thread never gets scheduled. At Warning or below, the test would be run and the Editor would have to be killed.

## Motivation

UTF2002 reports an async delegate whose constraint starts with `Throws`, where the author's intent is to test an exception and the fix is try/catch. The same delegate with any other constraint (`Is.EqualTo(1)`, `Is.Not.Null`, `Has.Count.EqualTo(3)`, `new EqualConstraint(1)`) is waited on through exactly the same path and freezes in exactly the same way, but the intent is different: the author wants the result of the operation, and the fix is to `await` it first. `Assume.That` has the same `ActualValueDelegate<TActual>` overloads and applies the constraint the same way, so it freezes too; it is reported here with every constraint, because UTF2002 does not cover it.

In the NUnit build bundled with Unity (`com.unity.ext.nunit`, based on NUnit 3.5), an async lambda converts to both `TestDelegate` (as `async void`) and `ActualValueDelegate<TActual>`; C# overload resolution prefers the delegate with a return type, so `Assert.That<TActual>(ActualValueDelegate<TActual>, IResolveConstraint)` is chosen with `TActual` = `Task` or `Task<TResult>`. That overload calls `Constraint.ApplyTo(ActualValueDelegate<TActual>)`, which checks the delegate with `AsyncInvocationRegion.IsAsyncOperation` and, for an async delegate, invokes it and calls `WaitForPendingOperationsToComplete`, which calls `Task.Wait()` on the calling thread. `DelayedConstraint` (`.After(...)`) polls the same `ApplyTo` of its base constraint, so it reaches the same wait. In Unity that thread is the main thread, and async continuations are posted to `UnitySynchronizationContext`, which is pumped by the main thread. The wait blocks the pump, the continuation never runs, and the Editor freezes. This is the same mechanism described in UTF1002, UTF1004, UTF2001, and UTF2002.

`ValueTask`, `UniTask`, and `Awaitable` do not pass NUnit's check unless the lambda has the `async` modifier: NUnit then compares the awaitable object itself against the constraint, and the assertion fails or passes for the wrong reason. With the `async` modifier, `WaitForPendingOperationsToComplete` looks up a parameterless `Wait` method by reflection and fails because none of these types has one. Neither shape freezes the Editor, but the assertion never checks what the author intended and the fix is the same `await`, so the rule reports every awaitable return type.

Whether a given `Task` actually deadlocks depends on its awaits: a task whose continuations all run off the main thread (for example, with `ConfigureAwait(false)` everywhere) completes, but it still stalls the whole test run for its duration, and the analyzer cannot tell the two apart.

The split between UTF2002 and UTF2003 is on the constraint expression, not on the delegate: every async delegate passed to `Assert.That` is reported by exactly one of the two rules, and every async delegate passed to `Assume.That` is reported by UTF2003. UTF2002 owns the calls whose constraint is syntactically rooted in `Throws` or constructs a `ThrowsConstraint`/`ThrowsNothingConstraint` directly; UTF2003 owns everything else, including a `Throws` constraint that arrives through a variable, field, parameter, or method return value. For those, the message of UTF2003 still points at the right direction: once the operation is awaited in an `async Task` test method, the exception surfaces where try/catch can handle it.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers 3.9.0 has no rule about an async delegate as the actual value of `Assert.That` or `Assume.That`. NUnit2021 (EqualToIncompatibleTypes) and NUnit2022 (SomeItemsIncompatibleTypes) reason about the *resolved* actual type (`Task<int>` is unwrapped to `int`, since NUnit awaits the delegate on a regular .NET test host), so they consider the call valid. The freeze is specific to Unity's main-thread synchronization context.

## Bad

```csharp
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public void Freezes()
    {
        Assert.That(async () => await GetAsync(), Is.EqualTo(1));   // UTF2003; freezes the Editor
        Assert.That(() => GetAsync(), Is.GreaterThan(0));   // UTF2003; reported even without the async modifier, the delegate returns Task<int>
        Assert.That(GetAsync, Is.Not.Null.After(100, 10));   // UTF2003; method group of a Task-returning method
        Assume.That(async () => await GetAsync(), Is.EqualTo(1));   // UTF2003; Assume.That freezes the same way
    }

    private static async Task<int> GetAsync()
    {
        await Task.Yield();
        return 1;
    }
}
```

## Good

```csharp
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public async Task AwaitThenAssert()
    {
        var actual = await GetAsync();
        Assume.That(actual, Is.EqualTo(1));
        Assert.That(actual, Is.EqualTo(1));
    }

    [Test]
    public void SynchronousDelegatesAreFine()
    {
        Assert.That(() => Get(), Is.EqualTo(1));
    }

    private static async Task<int> GetAsync()
    {
        await Task.Yield();
        return 1;
    }

    private static int Get() => 1;
}
```

## Notes

- A delegate argument is treated as async by the same criteria as UTF2002: the delegate type the argument converts to has an awaitable return type (`Task`, `Task<TResult>`, `ValueTask`, `UniTask`, `Awaitable`, or any other type with an instance `GetAwaiter()` method), or the argument is a lambda, anonymous method, or method group with the `async` modifier. This covers lambdas, method groups, and variables or fields of a delegate type (e.g. `Func<Task<int>>`).
- For `Assert.That`, the constraint is *not* inspected beyond the exclusion for UTF2002: the call is reported unless the constraint expression starts with a member of `NUnit.Framework.Throws` or is `new ThrowsConstraint(...)`/`new ThrowsNothingConstraint()`. A constraint held in a local, field, parameter, or returned from a method is reported here even when it is a `Throws` constraint.
- For `Assume.That`, the constraint is not inspected at all; every async delegate is reported.
- Passing the `Task` itself instead of a delegate (`Assert.That(GetAsync(), Is.EqualTo(1))`) is out of scope; NUnit compares the `Task` object and NUnit2021 reports the type mismatch.
- `Assert.That(bool)`, `Assert.That(bool, string)`, `Assert.That(Func<bool>, ...)`, and the same `Assume.That` overloads are not affected: a `Func<bool>` is not awaitable.
- A return type that is awaitable only through an extension-method `GetAwaiter` is not detected; the rule looks for an instance `GetAwaiter()` method.
- `ConfigureAwait(false)` does not exempt the delegate; the rule inspects the delegate's shape and does not inspect the awaits.
- The delegate argument and the constraint argument are located by parameter type, not by position, so the message overloads `Assert.That(del, expr, message, args)` and `Assume.That(del, expr, message, args)` are matched the same way as the two-argument form.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF2003.severity = warning
```
