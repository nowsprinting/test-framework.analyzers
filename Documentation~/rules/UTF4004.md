# UTF4004 — Waiting for a fixed time in test, setup, and teardown methods is not recommended

Detects a test, setup, or teardown method that waits for a fixed time instead of for a condition: a `yield return` of a `WaitForSeconds` or `WaitForSecondsRealtime`, an `await` of `UniTask.Delay`, `UniTask.WaitForSeconds`, `Task.Delay`, or `Awaitable.WaitForSecondsAsync`, and a call to `Thread.Sleep`. A fixed wait is chosen to cover the time a state transition takes on the author's machine, so the test fails when the environment is slower and wastes the surplus when it is faster.

| Item     | Value     |
|----------|-----------|
| Category | Style     |
| Enabled  | True      |
| Severity | Warning   |
| CodeFix  | False     |

Message: "'{0}' waits for a fixed time: the test fails when the environment is slower than expected and wastes time when it is faster. Wait for the condition instead."

`{0}` is the API that waits: `WaitForSeconds`, `WaitForSecondsRealtime`, `UniTask.Delay`, `UniTask.WaitForSeconds`, `Task.Delay`, `Awaitable.WaitForSecondsAsync`, or `Thread.Sleep`.

The diagnostic is reported at the operand of the `yield return` statement, at the `UniTask.Delay(...)` / `Task.Delay(...)` / `Awaitable.WaitForSecondsAsync(...)` invocation, or at the `Thread.Sleep(...)` invocation, when the wait appears in a test method or in a `SetUp`, `TearDown`, `OneTimeSetUp`, `OneTimeTearDown`, `UnitySetUp`, `UnityTearDown`, `UnityOneTimeSetUp`, or `UnityOneTimeTearDown` method, including inside a lambda or local function declared in such a method. A method with several waits gets one diagnostic per wait.

Helpers are followed to a bounded depth, with the same walk as UTF4001 and UTF4003. The test or hook method body is depth 0. An invocation that is the operand of `await` or `yield return` and resolves to a method with a body in the same compilation is walked at depth + 1, and a lambda or local function declared in the body being walked is walked at depth + 1 as well. Bodies at depth 3 and deeper are not walked. As in UTF4003, a wait found in a helper is reported at the wait inside the helper, not at the call site, because the fix is applied at the wait itself; a helper called from several places is reported once.

Severity is Warning because the test runs and, on the author's machine, passes. Nothing has to be stopped before the run; the rule reports a design choice that makes the test slow and environment-dependent.

## Motivation

A test that drives a state transition and then waits for it is often written with a fixed wait that is "long enough":

```csharp
StartFadeOut();
yield return new WaitForSeconds(1f);
Assert.That(_faded, Is.True);
```

The value is chosen against the machine the test is written on. On a slower machine, a loaded CI agent, or a device where the transition takes longer, the condition is not yet true when the wait ends and the test fails without a defect in the code under test. The usual response is to lengthen the wait, which makes every run on every machine wait the full value even when the transition completes in a few frames, and a suite with many such waits spends most of its time sleeping. Neither the flakiness nor the wasted time has a stable fix as long as the wait is a fixed duration, because no single value is both short enough to be cheap and long enough to be safe everywhere.

Waiting for the condition itself has neither problem. The wait ends as soon as the transition completes, and it fails only when the transition never completes. Unity Test Framework runs frames while a coroutine-style or `async Task` test method yields or awaits (see [Async tests](https://docs.unity3d.com/Manual/test-framework/reference-async-tests.html)), so a predicate wait is written as `yield return new WaitUntil(() => _faded)` or `await UniTask.WaitUntil(() => _faded)`, or as a `while` loop that yields or awaits.

The recognized APIs are the ones that complete after a duration given by the caller:

- `System.Threading.Tasks.Task.Delay(int)`, `Task.Delay(int, CancellationToken)`, `Task.Delay(TimeSpan)`, and `Task.Delay(TimeSpan, CancellationToken)` (verified against .NET Standard 2.0).
- `System.Threading.Thread.Sleep(int)` and `Thread.Sleep(TimeSpan)` (verified against .NET Standard 2.0). A `Thread.Sleep` stalls the main thread, so no frame advances while it waits and a condition driven by the main thread cannot become true during it; it is nevertheless a fixed wait and is reported by this rule with the others, since the fix is the same.
- `UnityEngine.WaitForSeconds(float seconds)` and `UnityEngine.WaitForSecondsRealtime(float time)`, yielded from a coroutine-style method (verified against the Unity 6000.4 Script Reference).
- `UnityEngine.Awaitable.WaitForSecondsAsync(float seconds, CancellationToken cancellationToken)` (verified against the Unity 6000.4 Script Reference).
- `Cysharp.Threading.Tasks.UniTask.Delay`, all four overloads (`int millisecondsDelay` or `TimeSpan delayTimeSpan`, with or without a `DelayType`), and `UniTask.WaitForSeconds(float duration, ...)` and `UniTask.WaitForSeconds(int duration, ...)` (verified against UniTask 2.5.11).

A `CancellationToken` argument does not change the verdict: the test runner never cancels the token, and the analyzer cannot tell whether the caller does. A `PlayerLoopTiming`, `DelayType`, or `ignoreTimeScale` argument does not change it either; they change which clock measures the duration, not that the duration is fixed.

### Why a fixed wait inside a while or do loop is not reported

A predicate wait written as a loop needs something to yield or await in its body, and a short fixed wait is a common choice for the polling interval:

```csharp
while (!_faded)
{
    yield return new WaitForSeconds(0.1f);
}
```

The loop is the wait, and it ends when the condition holds; the fixed wait inside sets only how often the condition is checked. The loop is covered by UTF4001 (test method without `Timeout`), UTF4002 (setup or teardown method without a time limit of its own), and UTF4003 (a body that only sleeps), so this rule does not report a fixed wait anywhere inside the body of a `while` or `do` loop. This also makes UTF4003 and UTF4004 mutually exclusive by construction: `while (!_faded) Thread.Sleep(10);` is reported at `while` by UTF4003 and not at `Thread.Sleep` by this rule.

A `for` or `foreach` loop is not a predicate wait; `for (var i = 0; i < 10; i++) yield return new WaitForSeconds(1f);` is a ten-second fixed wait in disguise, and the wait inside it is reported.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule about fixed waits. Verified with NUnit.Analyzers 3.9.0: the analyzer assembly contains no reference to `Task.Delay`, `Thread.Sleep`, or any delay-shaped rule. UTF2005 reports NUnit's own fixed wait, `DelayedConstraint`, for a different reason: it stalls the main thread.

## Bad

```csharp
using System;
using System.Collections;
using System.Threading;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _faded;
    private readonly WaitForSeconds _oneSecond = new WaitForSeconds(1f);

    [UnityTest]
    public IEnumerator WaitForSecondsInCoroutine()
    {
        StartFadeOut();
        yield return new WaitForSeconds(1f);   // UTF4004; too short on a slow machine, too long on a fast one
        Assert.That(_faded, Is.True);
    }

    [UnityTest]
    public IEnumerator WaitForSecondsRealtimeInCoroutine()
    {
        StartFadeOut();
        yield return new WaitForSecondsRealtime(1f);   // UTF4004
        Assert.That(_faded, Is.True);
    }

    [UnityTest]
    public IEnumerator CachedWaitForSeconds()
    {
        StartFadeOut();
        yield return _oneSecond;   // UTF4004; recognized by the type of the yielded value
        Assert.That(_faded, Is.True);
    }

    [Test]
    public async Task UniTaskDelayInAsync()
    {
        StartFadeOut();
        await UniTask.Delay(1000);   // UTF4004
        Assert.That(_faded, Is.True);
    }

    [Test]
    public async Task UniTaskWaitForSecondsInAsync()
    {
        StartFadeOut();
        await UniTask.WaitForSeconds(1f, ignoreTimeScale: true);   // UTF4004
        Assert.That(_faded, Is.True);
    }

    [Test]
    public async Task TaskDelayInAsync()
    {
        StartFadeOut();
        await Task.Delay(TimeSpan.FromSeconds(1));   // UTF4004
        Assert.That(_faded, Is.True);
    }

    [Test]
    public async Task AwaitableInAsync()
    {
        StartFadeOut();
        await Awaitable.WaitForSecondsAsync(1f);   // UTF4004
        Assert.That(_faded, Is.True);
    }

    [Test]
    public void ThreadSleep()
    {
        StartFadeOut();
        Thread.Sleep(1000);   // UTF4004; also stalls the Editor for the whole second
        Assert.That(_faded, Is.True);
    }

    [UnityTest]
    public IEnumerator FixedWaitInForLoop()
    {
        StartFadeOut();
        for (var i = 0; i < 10; i++)
        {
            yield return new WaitForSeconds(0.1f);   // UTF4004; a for loop does not wait for a condition
        }
        Assert.That(_faded, Is.True);
    }

    [UnitySetUp]
    public IEnumerator SetUp()
    {
        StartFadeOut();
        yield return new WaitForSeconds(1f);   // UTF4004; reported in hook methods too
    }

    [Test]
    public async Task FixedWaitInLambda()
    {
        StartFadeOut();
        Func<UniTask> settle = async () =>
        {
            await UniTask.Delay(1000);   // UTF4004; reported inside the lambda (depth 1)
        };
        await settle();
        Assert.That(_faded, Is.True);
    }

    [UnityTest]
    public IEnumerator FixedWaitInHelper()
    {
        StartFadeOut();
        yield return Settle();   // not reported here; the wait inside the helper is reported (depth 1)
        Assert.That(_faded, Is.True);
    }

    private IEnumerator Settle()
    {
        yield return new WaitForSeconds(1f);   // UTF4004; reported at the wait, once, however many callers the helper has
    }

    private void StartFadeOut()
    {
        // Sets _faded from a coroutine or Update several frames later
    }
}
```

## Good

```csharp
using System;
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _faded;

    [UnityTest]
    [Timeout(5000)]   // fails after five seconds when the flag is never set, as UTF4001 requires
    public IEnumerator WaitUntilInCoroutine()
    {
        StartFadeOut();
        yield return new WaitUntil(() => _faded);   // ends as soon as the transition completes
        Assert.That(_faded, Is.True);
    }

    [Test]
    [Timeout(5000)]
    public async Task UniTaskWaitUntilInAsync()
    {
        StartFadeOut();
        await UniTask.WaitUntil(() => _faded);
        Assert.That(_faded, Is.True);
    }

    [UnityTest]
    [Timeout(5000)]
    public IEnumerator PollingLoop()
    {
        StartFadeOut();
        while (!_faded)
        {
            yield return new WaitForSeconds(0.1f);   // not reported; the polling interval of a loop that waits for the condition
        }
        Assert.That(_faded, Is.True);
    }

    [Test]
    public async Task UniTaskTimeoutChain()   // bounded by itself, no Timeout attribute needed
    {
        StartFadeOut();
        await UniTask.WaitUntil(() => _faded).Timeout(TimeSpan.FromSeconds(5));
        Assert.That(_faded, Is.True);
    }

    [UnitySetUp]
    public IEnumerator SetUp()
    {
        StartFadeOut();
        yield return new WaitUntil(() => _faded, TimeSpan.FromSeconds(5), () => { }, WaitTimeoutMode.Realtime);   // a time limit of its own, as UTF4002 requires
    }

    [Test]
    public async Task AdvancesOneFrame()   // waits for no transition; not a fixed wait
    {
        await UniTask.NextFrame();
        await Task.Yield();
    }

    private void StartFadeOut()
    {
        // Sets _faded from a coroutine or Update several frames later
    }
}
```

## Notes

- A test method is recognized the way NUnit builds tests, as in UTF4001: a method with an attribute implementing `ITestBuilder` or `ISimpleTestBuilder` (`[Test]`, `[UnityTest]`, `[TestCase]`, and user-defined builders). A hook method is a method with `[SetUp]`, `[TearDown]`, `[OneTimeSetUp]`, `[OneTimeTearDown]`, `[UnitySetUp]`, `[UnityTearDown]`, `[UnityOneTimeSetUp]`, or `[UnityOneTimeTearDown]`, applied to the method itself or to a base declaration it overrides, as in UTF4003; the return type of the hook method is not checked. A fixed wait in any other method is not reported unless the method is reached through the walk.
- A `yield return` is recognized by the type of its operand, `UnityEngine.WaitForSeconds` or `UnityEngine.WaitForSecondsRealtime`, so a yield instruction cached in a field or a local is reported as well as `new WaitForSeconds(...)` written inline. A `new WaitForSeconds(...)` that is not yielded (assigned to a field, passed to another method) is not reported.
- An `await` is recognized when its operand is an invocation of a listed method, or a member-access chain whose innermost receiver is one (`await Task.Delay(100).ConfigureAwait(false)`, `await UniTask.Delay(100).SuppressCancellationThrow()`). A delay stored in a variable and awaited later (`var delay = UniTask.Delay(100); await delay;`) is not seen.
- `Thread.Sleep` is recognized wherever it is invoked in a walked body, not only as an `await` or `yield return` operand. UTF4003 reports a `while` or `do` loop whose body only sleeps; this rule reports a `Thread.Sleep` outside such a loop.
- A fixed wait anywhere inside the body of a `while` or `do` loop is not reported, also when nested in an `if` or a block, because the loop is a predicate wait and UTF4001, UTF4002, and UTF4003 cover it. The exclusion does not extend into a lambda or local function declared in the loop body; such a body is walked on its own.
- A fixed wait inside a `for` or `foreach` loop is reported once per wait, at the wait.
- The duration is not analyzed. `WaitForSeconds(0f)`, `Task.Delay(0)`, and `UniTask.Delay(0)` are reported like any other value; write `yield return null`, `await UniTask.NextFrame()`, or `await Task.Yield()` to advance a frame without a fixed wait. A duration taken from a variable, a constant, or a method call is reported the same way.
- Waits that count frames rather than time are not reported: `yield return null`, `UniTask.NextFrame()`, `UniTask.DelayFrame(n)`, `Task.Yield()`, `Awaitable.NextFrameAsync()`, `WaitForEndOfFrame`, `WaitForFixedUpdate`, and a `for` loop that yields `null` a fixed number of times. A large frame count is as fragile as a fixed time, but the rule has no threshold to tell a one-frame advance from a wait.
- Awaiting a `Task`, `UniTask`, or `Awaitable` returned by other code is never reported, including `Task.WhenAll`, `UniTask.WhenAny`, and a `Task.Delay` wrapped in a helper method that is not reached by the walk.
- A fixed wait is sometimes the subject of the test rather than a way to wait for a transition, e.g. a test that a cooldown expires after one second. Where the transition is observable, waiting for it with a `Timeout` attribute is still the more robust test; where it is not, suppress the diagnostic at that site with `#pragma warning disable UTF4004`, or drive the time from a fake clock so that the test does not wait at all.
- NUnit's `DelayedConstraint` (`Is.True.After(1000)`) is a fixed wait too, but it is reported by UTF2005 as an Error because it stalls the main thread; this rule does not report it a second time.
- Helpers are followed only through `await` and `yield return` operands (`yield return Settle();`), only when the helper has a body in the same compilation, and only two levels deep, with the same limits as UTF4001 and UTF4003. A helper invoked as a plain statement (`Settle();`) is not seen through. A fixed wait in a helper declared in another file than the test or hook method that reaches it is reported at the wait, so the diagnostic belongs to a document that is not the one being analyzed; an IDE that analyzes open documents one at a time may show it only on build; the compiler reports it always.
- A lambda or local function declared in a walked body is walked whether or not it is invoked, so a fixed wait in a lambda that is stored but never called is still reported, and a wait at depth 3 (a lambda inside a lambda inside a lambda) is not.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF4004.severity = suggestion
```
