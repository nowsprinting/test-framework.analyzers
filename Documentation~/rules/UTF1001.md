# UTF1001 — TestCase and TestCaseSource are not supported on coroutine test methods

Detects `TestCaseAttribute` or `TestCaseSourceAttribute` placed on a test method whose return type is `System.Collections.IEnumerator` (a coroutine-style test method).

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "Method-level parameterized tests cannot be used on coroutine-style test methods. Use the `async` keyword instead."

Severity is Error because the test cannot run: NUnit marks the method as not runnable when it is loaded, so the test fails without exercising any of the code under test.

## Motivation

Unity Test Framework runs a test as a coroutine when its return type is `IEnumerator`. Such a test is supposed to be marked with `UnityTestAttribute`, and the [official documentation](https://docs.unity3d.com/6000.4/Documentation/Manual/test-framework/reference-tests-parameterized.html) states that Unity tests only support `ValueSourceAttribute` on parameters. Method-level parameterized attributes, `TestCaseAttribute` and `TestCaseSourceAttribute`, are not supported.

When one of these attributes is placed on an `IEnumerator` method, NUnit's test case builder rejects the method with the message "Method has non-void return value, but no result is expected" and sets its run state to `NotRunnable`. The test is reported as a failure, but the coroutine body never executes.

Unity Test Framework supports `async Task` test methods with `TestAttribute`, and `TestCaseAttribute` and `TestCaseSourceAttribute` work on them. Rewriting the coroutine as an `async Task` method (or a synchronous `void` method) gives method-level parameterized tests without workarounds.

### Why NUnit1007 cannot be used instead

NUnit.Analyzers reports NUnit1007 ("The method has non-void return type, but no result is expected in ExpectedResult") for `TestCaseAttribute` on a non-void method. It partially overlaps with this rule, but:

- Its suggested fix is to add `ExpectedResult` or return `void`. Setting `ExpectedResult` silences NUnit1007, but the coroutine is still not a supported parameterized form in Unity Test Framework.
- It does not mention `async Task`, which is the recommended rewrite for Unity Test Framework users.

## Bad

```csharp
using System.Collections;
using NUnit.Framework;
using UnityEngine.TestTools;

public class MyTest
{
    [TestCase(1)]
    [TestCase(2)]
    public IEnumerator MyCoroutineTest(int value)   // UTF1001
    {
        yield return null;
        Assert.That(value, Is.GreaterThan(0));
    }

    private static readonly object[] s_cases = { 1, 2 };

    [TestCaseSource(nameof(s_cases))]
    public IEnumerator MyCoroutineTestWithSource(int value)   // UTF1001
    {
        yield return null;
        Assert.That(value, Is.GreaterThan(0));
    }
}
```

## Good

```csharp
using System.Collections;
using System.Threading.Tasks;
using NUnit.Framework;
using UnityEngine.TestTools;

public class MyTest
{
    [TestCase(1)]
    [TestCase(2)]
    public async Task MyAsyncTest(int value)
    {
        await Task.Yield();
        Assert.That(value, Is.GreaterThan(0));
    }

    [TestCase(1)]
    [TestCase(2)]
    public void MySyncTest(int value)
    {
        Assert.That(value, Is.GreaterThan(0));
    }

    private static readonly int[] s_values = { 1, 2 };

    [UnityTest]
    public IEnumerator MyCoroutineTest([ValueSource(nameof(s_values))] int value)
    {
        yield return null;
        Assert.That(value, Is.GreaterThan(0));
    }
}
```

## Notes

- The rule matches only when the return type is exactly `System.Collections.IEnumerator`, the same condition Unity Test Framework uses to decide to run a method as a coroutine. `IEnumerator<T>` and `IEnumerable` are not matched.
- Whether `UnityTestAttribute` is present, and whether `ExpectedResult` is set on `TestCaseAttribute`, do not affect the diagnostic.
- Parameter-level attributes (`ValueSourceAttribute`, `ValuesAttribute`, `RangeAttribute`) are out of scope for this rule.

To change the severity, add the following to `.editorconfig`:

```editorconfig
dotnet_diagnostic.UTF1001.severity = warning
```
