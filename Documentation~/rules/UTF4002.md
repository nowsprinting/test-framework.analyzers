# UTF4002 — Waits for a condition in UnitySetUp, UnityTearDown, UnityOneTimeSetUp, UnityOneTimeTearDown, SetUp, and TearDown methods must have a time limit

Detects a setup or teardown method that waits for a condition with no time limit of its own. Two shapes are recognized, the same as in UTF4001: a `while` or `do` loop that yields or awaits in its body, and a call to a predicate-wait API (`WaitUntil`, `WaitWhile`, and the `UniTask.WaitUntil` family) that is not bounded by a timeout. When the condition never holds, the test run hangs: Unity Test Framework checks the `Timeout` attribute and its 180-second default only while the test method body runs, never while a setup or teardown method runs.

| Item     | Value     |
|----------|-----------|
| Category | Style     |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' waits for a condition without a time limit in a method marked with '{1}': the test run hangs when the condition never holds, and a Timeout attribute does not interrupt it. Give the wait a time limit of its own, e.g. a WaitUntil with a TimeSpan timeout or a for loop."

`{0}` is the construct that waits: `while` or `do` for a loop, the name of the invoked API, e.g. `WaitUntil`, `WaitWhile`, `UniTask.WaitUntil`, `UniTask.WaitUntilValueChanged`, or the name of a helper method in the same compilation that waits inside, e.g. `WaitForSceneLoaded`. `{1}` is the type name of the attribute that marks the method, e.g. `UnitySetUpAttribute`.

The diagnostic is reported at each waiting construct, at the same locations as UTF4001: the `while` or `do` keyword of the loop (also when the loop is inside a lambda or a local function declared in the method), the `new WaitUntil(...)` / `new WaitWhile(...)` object creation, the `UniTask.WaitUntil(...)` invocation, or the invocation of a helper method that waits. A method with several waits gets one diagnostic per wait.

Helpers are followed to a bounded depth, as in UTF4001. The setup or teardown method body is depth 0. An invocation that is the operand of `await` or `yield return` and resolves to a method with a body in the same compilation is walked at depth + 1, and a lambda or local function declared in the body being walked is walked at depth + 1 as well. Bodies at depth 3 and deeper are not walked.

Severity is Error because nothing ends the wait. A test method without `Timeout` is stopped after 180 seconds (UTF4001); a setup or teardown method is not stopped at all, so the Editor or the player stays in the test run until someone cancels it, and a CI job runs until the CI system's own limit.

## Motivation

A fixture often prepares its scene in a setup method and waits for the preparation to complete:

```csharp
[UnitySetUp]
public IEnumerator SetUp()
{
    SceneManager.LoadScene("Stage");
    while (!_stageReady) yield return null;
}
```

When the preparation works, the condition holds within a few frames. When it does not, nothing in the method ends the wait, and unlike a test method, nothing outside the method ends it either.

Unity Test Framework enforces the `Timeout` attribute and its 180-second default (`UnityWorkItem.k_DefaultTimeout`) by polling `UnityTestExecutionContext.HasTimedOut()` after each step of the test method body: in `EnumerableTestMethodCommand` for coroutine-style test methods, in `TaskTestMethodCommand` for `async Task` test methods, and once after the method returns in `UnityTestMethodCommand` for synchronous test methods. Setup and teardown methods are run by `BeforeAfterTestCommandBase.ExecuteEnumerable`, which `EnumerableSetUpTearDownCommand` (`[UnitySetUp]`, `[UnityTearDown]`), `EnumerableOneTimeSetUpTearDownCommand` (`[UnityOneTimeSetUp]`, `[UnityOneTimeTearDown]`), and `SetUpTearDownCommand` (`[SetUp]`, `[TearDown]`, including the `async Task` form) derive from. That loop advances the method's enumerator, or polls the returned `Task`, and never consults `HasTimedOut()`. A `TimeoutCommand` class exists in the package but is not part of the command chain that `TestCommandBuilder.BuildTestCommand` builds. Verified against Unity Test Framework 1.6.0 source.

The clock behind `HasTimedOut()` is `UnityTestExecutionContext.StartTicks`, set in `UnityWorkItem.Execute()` before the command chain starts, so the time spent in `[SetUp]`, `[UnitySetUp]`, and their teardown counterparts does count toward the test's `Timeout` once the test method body runs. The limit is therefore reached after a slow setup, at the first yield of the test method, but it is never reached inside a setup or teardown method that does not return. `[UnityOneTimeSetUp]` and `[UnityOneTimeTearDown]` run on the fixture's own work item and context, so their time is not counted against any test.

Because a `Timeout` attribute cannot help, the fix for a setup or teardown method is different from UTF4001: the wait itself needs a time limit. Unity provides the `WaitUntil` and `WaitWhile` constructors that take a `TimeSpan timeout`, an `Action onTimeout`, and a `WaitTimeoutMode` (present in the Script Reference of Unity 6000.0 through 6000.6; earlier versions were not checked). UniTask provides the `Timeout(TimeSpan)` and `TimeoutWithoutException(TimeSpan)` extension methods on `UniTask` and `UniTask<T>`, which throw `TimeoutException` or return a flag when the awaited task does not complete in time (verified against UniTask 2.5.11). A loop that counts frames can be written as a `for` loop, and a loop that checks a deadline compares a clock in its condition.

### Why the rule is separate from UTF4001

Both rules recognize the same waiting shapes with the same walk, but the consequence and the fix differ. UTF4001 reports a test method and asks for a `Timeout` attribute, which ends the wait after the given time. UTF4002 reports a setup or teardown method, where a `Timeout` attribute changes nothing, and asks for a bounded wait. A single rule would either give the wrong fix in one of the two cases or need two messages under one title; two rules also let a project set a different severity for each.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule about waits in setup or teardown methods, and none about `TimeoutAttribute`. On a regular .NET test host a stuck setup blocks only its worker thread.

## Bad

```csharp
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.TestTools;

[Timeout(5000)]   // covers the test methods only; the waits below are still reported
public class MyTest
{
    private bool _stageReady;

    [UnityOneTimeSetUp]
    public IEnumerator OneTimeSetUp()
    {
        SceneManager.LoadScene("Stage", LoadSceneMode.Additive);
        while (!_stageReady)   // UTF4002; the run hangs when the flag is never set
        {
            yield return null;
        }
    }

    [UnitySetUp]
    public IEnumerator SetUp()
    {
        ResetStage();
        yield return new WaitUntil(() => _stageReady);   // UTF4002
    }

    [SetUp]
    public async Task SetUpAsync()
    {
        ResetStage();
        await UniTask.WaitUntil(() => _stageReady);   // UTF4002
    }

    [UnityTearDown]
    public IEnumerator TearDown()
    {
        yield return WaitForStage();   // UTF4002; the helper loops until the flag is set (depth 1)
    }

    [UnityTest]
    public IEnumerator Test()
    {
        yield return null;
    }

    private IEnumerator WaitForStage()
    {
        while (!_stageReady)
        {
            yield return null;
        }
    }

    private void ResetStage()
    {
        // Sets _stageReady from a coroutine or Update several frames later
    }
}
```

## Good

```csharp
using System;
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _stageReady;

    [UnityOneTimeSetUp]
    public IEnumerator OneTimeSetUp()
    {
        SceneManager.LoadScene("Stage", LoadSceneMode.Additive);
        for (var i = 0; i < 300 && !_stageReady; i++)   // gives up after 300 frames
        {
            yield return null;
        }
        Assert.That(_stageReady, Is.True);
    }

    [UnitySetUp]
    public IEnumerator SetUp()
    {
        ResetStage();
        yield return new WaitUntil(() => _stageReady, TimeSpan.FromSeconds(5), () => { }, WaitTimeoutMode.Realtime);
        Assert.That(_stageReady, Is.True);
    }

    [SetUp]
    public async Task SetUpAsync()
    {
        ResetStage();
        await UniTask.WaitUntil(() => _stageReady).Timeout(TimeSpan.FromSeconds(5));   // throws TimeoutException
    }

    [UnityTearDown]
    public IEnumerator TearDown()
    {
        yield return SceneManager.UnloadSceneAsync("Stage");   // a finite engine operation, not a condition
    }

    [UnityTest]
    public IEnumerator Test()
    {
        yield return null;
    }

    private void ResetStage()
    {
        // Sets _stageReady from a coroutine or Update several frames later
    }
}
```

## Notes

- A method is recognized by the attribute that marks it and by the return type Unity Test Framework runs for that attribute: `UnitySetUpAttribute`, `UnityTearDownAttribute`, `UnityOneTimeSetUpAttribute`, or `UnityOneTimeTearDownAttribute` on a method returning `IEnumerator`, and `SetUpAttribute` or `TearDownAttribute` on a method returning `Task`. The attribute may be applied to the method itself or to a base declaration it overrides.
- Other return types are not inspected, because the framework does not run the method as a coroutine: a `[UnitySetUp]` method that returns `Task` is skipped by `EnumerableSetUpTearDownCommand` (it collects `IEnumerator` methods only), and an `async void` `[SetUp]` method is invoked synchronously by `SetUpTearDownCommand` and returns at its first `await`, so its wait continues in the background and does not hang the run.
- `[OneTimeSetUp]` and `[OneTimeTearDown]` methods are not inspected. They are run synchronously by NUnit's own commands, so a coroutine or an await cannot appear in them except in the `async Task` form, which UTF1004 reports.
- A synchronous busy loop (`while (!ready) { }`) is out of scope, as in UTF4001: it never returns control to the test runner. It is planned to be reported by UTF4003.
- The following waits are bounded and are not reported:
  - A `WaitUntil` or `WaitWhile` created with the constructor that takes a `TimeSpan timeout`.
  - A `UniTask.WaitUntil` family invocation that is the receiver of `Timeout(...)` or `TimeoutWithoutException(...)`, e.g. `await UniTask.WaitUntil(() => ready).Timeout(TimeSpan.FromSeconds(5))`. A helper whose waits are all chained this way is bounded too.
  - A `for` or `foreach` loop, whatever it yields or awaits.
  - A deadline loop: a `while` or `do` loop whose condition reads a member of `UnityEngine.Time`, `System.DateTime`, `System.DateTimeOffset`, or `System.Diagnostics.Stopwatch` (`while (!ready && Time.time < deadline) yield return null;`), or whose condition references a local or field that the loop body assigns from such a member (`while (elapsed < 1f) { elapsed += Time.deltaTime; yield return null; }`). The direction of the comparison and the shape of the condition are not checked, as in UTF4001.
- A `CancellationToken` argument to a `UniTask.WaitUntil` family invocation does not make the wait bounded, and the invocation is reported. The test runner never cancels the token, and the analyzer cannot tell whether the caller does (e.g. with `CancellationTokenSource.CancelAfterSlim(TimeSpan)`); chain `Timeout(...)` instead.
- A `while` loop with a counter (`while (n-- > 0) yield return null;`) is reported although it is bounded, as in UTF4001. Write it as a `for` loop, or use a `WaitUntil` with a `TimeSpan` timeout.
- A `Timeout` attribute on the method, the fixture, or the assembly does not satisfy this rule, because it is not enforced while a setup or teardown method runs. The time a `[SetUp]`, `[UnitySetUp]`, `[TearDown]`, or `[UnityTearDown]` method takes is nevertheless charged to the test's `Timeout`, so a slow but finite setup makes the test fail at its first yield.
- Helpers are followed only through `await` and `yield return` operands, only when the helper has a body in the same compilation, and only two levels deep, with the same limits as UTF4001. A helper shared by a test method and a setup method is reported by UTF4001 at the call site in the test method and by UTF4002 at the call site in the setup method.
- Awaiting a `Task`, `UniTask`, or `Awaitable` returned by other code is never reported, including `TaskCompletionSource.Task` and UniTask async events, because the analyzer cannot know whether the awaited operation is bounded.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF4002.severity = warning
```
