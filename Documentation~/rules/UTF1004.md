# UTF1004 — OneTimeSetUp and OneTimeTearDown attributes are not supported on async methods

Detects a method marked with `OneTimeSetUpAttribute` or `OneTimeTearDownAttribute` whose return type is `System.Threading.Tasks.Task` (or `Task<TResult>`), or that has the `async` modifier. Unity Test Framework runs these methods through NUnit's synchronous command, so a `Task`-returning method freezes the Editor. An `async void` OneTimeSetUp fails and skips every test in the fixture; an `async void` OneTimeTearDown is recorded as a teardown error.

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported on methods that return Task or have the async modifier: the Editor freezes or the fixture fails. Use '{1}' with a coroutine-style method instead."

`{0}` is the type name of the offending attribute, and `{1}` is its replacement: `UnityOneTimeSetUpAttribute` for `OneTimeSetUpAttribute`, `UnityOneTimeTearDownAttribute` for `OneTimeTearDownAttribute`.

Severity is Error because running the fixture can freeze the Editor: the returned `Task` is waited on synchronously on the main thread, so any continuation that must run on the main thread never gets scheduled.

> [!IMPORTANT]\
> `UnityOneTimeSetUpAttribute` and `UnityOneTimeTearDownAttribute` are available only in Unity Test Framework 1.5.0 or later.
> Since Unity Test Framework 1.4.6, the package is a core package bundled with the Unity Editor and cannot be upgraded independently; 1.5.0 is bundled with Unity 6000.0.44f1 or later.

## Motivation

Unity Test Framework replaces NUnit's per-test setup and teardown commands with its own. `SetUpTearDownCommand` accepts `Task` as the return type of `[SetUp]` and `[TearDown]` methods and polls the task from a coroutine, so `async Task` works there (supported since Unity Test Framework 1.3.0). Because of this, it is natural to expect `[OneTimeSetUp]` and `[OneTimeTearDown]` to behave the same way. They do not.

`[OneTimeSetUp]` and `[OneTimeTearDown]` are executed by NUnit's `OneTimeSetUpCommand` and `OneTimeTearDownCommand`, which Unity Test Framework builds in `CompositeWorkItem` and calls synchronously (`PerformOneTimeSetUp` / `PerformOneTimeTearDown`). NUnit's `SetUpTearDownItem` treats a method as async when its return type starts with `System.Threading.Tasks.Task` or the method is marked with `AsyncStateMachineAttribute`, and handles the two cases as follows:

- **`Task` or `Task<TResult>` return type** (with or without the `async` modifier): NUnit calls `Task.Wait()` on the calling thread. In Unity that thread is the main thread, and async continuations are posted to `UnitySynchronizationContext`, which is pumped by the main thread. The wait blocks the pump, the continuation never runs, and the Editor freezes. `await Task.Yield()`, `await Task.Delay(...)`, `await Awaitable.NextFrameAsync()`, and awaiting any Unity API are enough to trigger it. This is the same mechanism described in UTF1002.
- **`async void`**: NUnit's `AsyncInvocationRegion.Create` throws `ArgumentException` ("'async void' methods are not supported, please use 'async Task' instead"; verified in the NUnit build bundled with Unity 6000.4). The Editor does not freeze, but a OneTimeSetUp is recorded as failed and every test in the fixture is skipped with the message "OneTimeSetUp: ...", and a OneTimeTearDown is recorded as a teardown error.

The rule matches on the method signature. Whether a given `Task` actually deadlocks depends on its awaits: a task whose continuations all run off the main thread (for example, with `ConfigureAwait(false)` everywhere) completes, but it still stalls the whole test run for its duration, and the analyzer cannot tell the two apart.

Unity Test Framework provides `UnityOneTimeSetUpAttribute` and `UnityOneTimeTearDownAttribute` for one-time setup that needs to wait. `EnumerableOneTimeSetUpTearDownCommand` runs them as coroutines, so `yield return null` and Unity yield instructions work. The [official documentation](https://docs.unity3d.com/Manual/test-framework/reference-unitysetup-and-unityteardown.html) states that they "expect a return type of `IEnumerator`". Rewriting the async method as an `IEnumerator` coroutine with one of these attributes is the supported alternative.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers inspects only test methods for async misuse: NUnit1012 and NUnit1013 look at methods marked with `TestAttribute` or `TestCaseAttribute`. The only rule that looks at setup and teardown method signatures is NUnit1026, which checks accessibility. No rule checks their return type or `async` modifier, so this defect is never reported. Verified with NUnit.Analyzers 3.9.0.

## Bad

```csharp
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [OneTimeSetUp]   // UTF1004; freezes the Editor
    public async Task OneTimeSetUp()
    {
        await Task.Yield();
    }

    [OneTimeTearDown]   // UTF1004; reported even without the async modifier, freezes when the task awaits on the main thread
    public Task OneTimeTearDown()
    {
        return CleanUpAsync();
    }

    private static async Task CleanUpAsync()
    {
        await Task.Yield();
    }

    [OneTimeSetUp]   // UTF1004; the OneTimeSetUp fails and every test in the fixture is skipped
    public async void OneTimeSetUpVoid()
    {
        await Task.Yield();
    }

    [Test]
    public void MyTestMethod()
    {
        Assert.That(true, Is.True);
    }
}
```

## Good

```csharp
using System.Collections;
using NUnit.Framework;
using UnityEngine.TestTools;

public class MyTest
{
    [UnityOneTimeSetUp]
    public IEnumerator UnityOneTimeSetUp()
    {
        yield return null;
    }

    [UnityOneTimeTearDown]
    public IEnumerator UnityOneTimeTearDown()
    {
        yield return null;
    }

    [OneTimeSetUp]   // synchronous methods are fine
    public void OneTimeSetUp()
    {
    }

    [Test]
    public void MyTestMethod()
    {
        Assert.That(true, Is.True);
    }
}
```

## Notes

- The rule matches any method marked with `OneTimeSetUpAttribute` or `OneTimeTearDownAttribute` that either returns `Task` or `Task<TResult>` for any `TResult`, or has the `async` modifier. The diagnostic is reported at each offending attribute.
- Only `OneTimeSetUpAttribute` and `OneTimeTearDownAttribute` themselves are matched; attributes derived from them are not detected.
- The rule is attribute-based, so it also covers methods in classes marked with `SetUpFixtureAttribute`, which Unity Test Framework runs through the same `CompositeWorkItem` path.
- `ConfigureAwait(false)` does not exempt the method; the rule is signature-based and does not inspect the awaits.
- `UnityOneTimeSetUpAttribute` and `UnityOneTimeTearDownAttribute` are available only in Unity Test Framework 1.5.0 or later. Since Unity Test Framework 1.4.6, the package is a core package bundled with the Unity Editor and cannot be upgraded independently; 1.5.0 is bundled with Unity 6000.0.44f1 or later. Projects on an earlier Editor cannot use the attributes named in the message without upgrading the Editor. This package depends on Unity Test Framework 1.4.6 so that it works on those Editors. On 1.4.x, the alternatives are a synchronous `[OneTimeSetUp]` / `[OneTimeTearDown]` method, or moving the asynchronous work to per-test `[UnitySetUp]` / `[UnityTearDown]` coroutines or `async Task` `[SetUp]` / `[TearDown]` methods.
- `[SetUp]` and `[TearDown]` methods returning `Task` are out of scope; Unity Test Framework supports them.
- A method carrying both `[OneTimeSetUp]` and `[OneTimeTearDown]` gets one diagnostic per attribute.
- `ValueTask` and other awaitable return types are matched only through the `async` modifier: a non-async `ValueTask` method is not reported, while an `async ValueTask` method is. This follows NUnit, which recognizes only `Task` / `Task<TResult>` (by full-name prefix) and `AsyncStateMachineAttribute`.
- `[UnityOneTimeSetUp]`, `[UnityOneTimeTearDown]`, `[UnitySetUp]`, and `[UnityTearDown]` methods whose return type is not `IEnumerator` are out of scope. Unity Test Framework silently ignores such methods, which is a different defect.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF1004.severity = warning
```
