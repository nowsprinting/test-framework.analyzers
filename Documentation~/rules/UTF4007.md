# UTF4007 — Async Task SetUp and TearDown methods are recommended over coroutine-style methods with the UnitySetUp and UnityTearDown attributes

Detects a coroutine-style setup or teardown method (a method marked with `UnitySetUpAttribute` or `UnityTearDownAttribute` whose return type is `System.Collections.IEnumerator`) whose every `yield return` yields `null` or a Unity yield instruction, so that the method can be written as an `async Task` method with `SetUpAttribute` or `TearDownAttribute`. A method that yields anything else, e.g. an Edit Mode instruction such as `EnterPlayMode` or an `IEnumerator` returned by the code under test, is not reported.

| Item     | Value     |
|----------|-----------|
| Category | Style     |
| Enabled  | True      |
| Severity | Warning   |
| CodeFix  | False     |

Message: "'{0}' is a coroutine-style method with the '{1}' attribute that yields only Unity yield instructions: it cannot catch an exception across a wait. Use an 'async Task' method with the '{2}' attribute instead."

`{0}` is the name of the method, `{1}` is the type name of the attribute that marks it (`UnitySetUpAttribute` or `UnityTearDownAttribute`), and `{2}` is the type name of its replacement (`SetUpAttribute` for `UnitySetUpAttribute`, `TearDownAttribute` for `UnityTearDownAttribute`).

The diagnostic is reported once per method, on the span from the return type through the method name (`IEnumerator SetUp`), which is what the rewrite changes, as in UTF4006.

Severity is Warning because the setup or teardown runs as written; nothing has to be stopped before the run. The rule reports a design choice that forgoes exception handling across a wait and mixes two styles of asynchronous code in one fixture. In a project with many coroutine-style setup methods written before `async Task` setup methods were supported, every one of them is reported at once; lower the severity to `suggestion` there (see Notes) and raise it back when the migration is done.

> [!WARNING]\
> A `[UnitySetUp]` method runs before every `[SetUp]` method, and a `[UnityTearDown]` method runs after every `[TearDown]` method (see [Execution order of test actions](https://docs.unity3d.com/Manual/test-framework/reference-actions-outside-tests.html)).
> When the fixture also has a `[SetUp]` or `[TearDown]` method, the rewritten method loses that position: NUnit does not define the order of several `[SetUp]` methods, or of several `[TearDown]` methods, declared on the same class.
> If the rewritten method depends on the existing one, or the other way round, merge the two into one `async Task` method so that the order stays explicit.

> [!WARNING]\
> When a domain reload happens during an Edit Mode test (the test yields `EnterPlayMode`, `ExitPlayMode`, `RecompileScripts`, or `WaitForDomainReload`), `[SetUp]` methods run again before the rest of the test, but `[UnitySetUp]` methods do not (see [UnitySetUp and UnityTearDown](https://docs.unity3d.com/Manual/test-framework/reference-unitysetup-and-unityteardown.html): "On domain reload, all non-Unity actions (such as OneTimeSetup and Setup) are rerun before the code that initiated the domain reload continues. Unity actions (such as UnitySetup) are not rerun.").
> A setup rewritten as `async Task` `[SetUp]` therefore runs once more after each domain reload in the test.
> Where that is not acceptable, e.g. the setup loads a scene or instantiates objects that the test expects to see once, keep the `[UnitySetUp]` method and suppress the diagnostic (see Notes).
> Teardown is not affected: `[TearDown]` and `[UnityTearDown]` both run once, after the second part of the test.

## Motivation

Unity Test Framework runs a `[SetUp]` or `[TearDown]` method that returns `Task` the same way it runs a `[UnitySetUp]` or `[UnityTearDown]` coroutine: `SetUpTearDownCommand` accepts `void` and `Task` as the return type, invokes the method on the main thread, and yields a frame until the task completes (supported since Unity Test Framework 1.3.0; verified against Unity Test Framework 1.6.0). Both forms run in Edit Mode and Play Mode. Where both forms express the same setup, the `async Task` form has the advantages that UTF4006 describes for test methods, except that method-level parameterized attributes do not apply to setup methods:

- An exception thrown across a wait can be caught. C# does not allow `yield return` inside a `try` block that has a `catch` clause (compiler error CS1626), so a coroutine-style setup cannot wait inside a `try` and fail with a message of its own when the code under test throws some frames later. `await` inside a `try` block with a `catch` clause is allowed.
- The fixture uses one style of asynchronous code. A fixture whose tests are `async Task` (UTF4006) and whose setup is a coroutine reads the same wait in two notations, and a `Task`, `UniTask`, or `Awaitable` returned by the code under test is awaited directly in the setup instead of being adapted to a coroutine.

Every yield instruction that Unity ships has an `await` counterpart; the conversion table in UTF4006 applies unchanged. A method that yields anything else is not reported, for the same reasons as in UTF4006: an `IEnumerator` returned by the code under test or by another package, a `Coroutine`, a `CustomYieldInstruction` declared outside the `UnityEngine` namespace, and an Edit Mode instruction (`EnterPlayMode`, `ExitPlayMode`, `RecompileScripts`, `WaitForDomainReload`) exempt the method. The Edit Mode instructions are the documented use of `[UnitySetUp]` and `[UnityTearDown]` (the [official documentation](https://docs.unity3d.com/Manual/test-framework/reference-unitysetup-and-unityteardown.html) states that the attributes "are equivalent to the NUnit `[SetUp]` and `[TearDown]` attributes, with the exception that they allow for yielding instructions for the Unity Editor"), and they have no async counterpart, so a setup that enters Play Mode stays a coroutine.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule about `IEnumerator` setup or teardown methods; `UnitySetUpAttribute` and `UnityTearDownAttribute` are Unity Test Framework extensions. Verified with NUnit.Analyzers 3.9.0.

## Bad

```csharp
using System.Collections;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.TestTools;

public class MyTest
{
    private FadePlayer _player;

    [UnitySetUp]
    public IEnumerator YieldNull()   // UTF4007
    {
        _player = new GameObject().AddComponent<FadePlayer>();
        yield return null;   // wait for Awake and Start
    }

    [UnitySetUp]
    public IEnumerator YieldAsyncOperation()   // UTF4007; AsyncOperation derives from YieldInstruction
    {
        yield return SceneManager.LoadSceneAsync("Main");
    }

    [UnitySetUp]
    public IEnumerator YieldFixtureHelper()   // UTF4007; the helper is an iterator declared in the fixture and yields only null
    {
        yield return WaitForPlayer();
    }

    [UnityTearDown]
    public IEnumerator YieldWaitUntil()   // UTF4007
    {
        _player.FadeOut();
        yield return new WaitUntil(() => _player.Faded);
        Object.Destroy(_player.gameObject);
    }

    [Test]
    public void Test()
    {
        Assert.That(_player, Is.Not.Null);
    }

    private IEnumerator WaitForPlayer()
    {
        for (var i = 0; i < 3; i++)
        {
            yield return null;
        }
    }
}
```

## Good

```csharp
using System;
using System.Collections;
using System.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.TestTools;

public class MyTest
{
    private FadePlayer _player;

    [SetUp]
    public async Task SetUp()
    {
        try
        {
            await Awaitable.FromAsyncOperation(SceneManager.LoadSceneAsync("Main"));   // catching across a wait is not possible with yield return
        }
        catch (Exception e)
        {
            Assert.Fail($"Scene load failed: {e.Message}");
        }

        _player = new GameObject().AddComponent<FadePlayer>();
        await Awaitable.NextFrameAsync();
    }

    [TearDown]
    public async Task AwaitTaskUnderTest()
    {
        await _player.FadeOutAsync();   // a Task returned by the code under test is awaited directly
        Object.Destroy(_player.gameObject);
    }

    [Test]
    public void Test()
    {
        Assert.That(_player, Is.Not.Null);
    }
}

public class EditModeTest
{
    [UnitySetUp]
    public IEnumerator YieldEnterPlayMode()   // Edit Mode instruction, no async counterpart
    {
        yield return new EnterPlayMode();
    }

    [UnityTearDown]
    public IEnumerator YieldExitPlayMode()
    {
        yield return new ExitPlayMode();
    }

    [Test]
    public void Test()
    {
        Assert.That(Application.isPlaying, Is.True);
    }
}

public class CoroutineUnderTest
{
    private FadePlayer _player;

    [UnitySetUp]
    public IEnumerator YieldCoroutineUnderTest()   // the setup target is a coroutine
    {
        _player = new GameObject().AddComponent<FadePlayer>();
        yield return _player.FadeIn();
    }

    [UnityTearDown]
    public IEnumerator YieldStartCoroutine()   // Coroutine is excluded
    {
        yield return _player.StartCoroutine(_player.FadeOut());
        Object.Destroy(_player.gameObject);
    }

    [Test]
    public void Test()
    {
        Assert.That(_player.Faded, Is.False);
    }
}

public class MergedSetUp
{
    private FadePlayer _player;

    [SetUp]
    public async Task SetUp()   // a former UnitySetUp body and a former SetUp body that depends on it, merged so that the order stays explicit
    {
        _player = new GameObject().AddComponent<FadePlayer>();
        await Awaitable.NextFrameAsync();

        _player.Reset();
    }

    [Test]
    public void Test()
    {
        Assert.That(_player.Faded, Is.False);
    }
}
```

## Notes

- A method is recognized by the attribute that marks it and by the return type Unity Test Framework runs for that attribute, as in UTF4002: `UnitySetUpAttribute` or `UnityTearDownAttribute` on a method returning `System.Collections.IEnumerator`. The attribute may be applied to the method itself or to a base declaration it overrides. A `[UnitySetUp]` method that returns anything else is not run by the framework and is not reported; UTF1009 reports it.
- `[UnityOneTimeSetUp]` and `[UnityOneTimeTearDown]` methods are not reported. Their `async Task` counterparts, `[OneTimeSetUp]` and `[OneTimeTearDown]`, are run synchronously and freeze the Editor (UTF1004), so the coroutine is the only form that can wait there.
- Which yields are convertible, which exempt the method, how helpers are followed, and how lambdas, local functions, non-iterator methods, and methods without `yield return` are treated is the same as in UTF4006. In particular:
  - A yielded value is recognized by its static type as the `null` literal or a type deriving from `UnityEngine.YieldInstruction` or `UnityEngine.CustomYieldInstruction` declared in the `UnityEngine` namespace or a namespace under it, excluding `UnityEngine.Coroutine`. Anything else exempts the method.
  - Helpers are followed only through `yield return` operands that are direct invocations, only when the helper is an iterator declared in the fixture or one of its base types, and only two levels deep. An operand the walk cannot see through exempts the method.
  - A method with no `yield return` at all is reported: a `void` method with `[SetUp]` or `[TearDown]` is as good a replacement as an `async Task` one.
- An `IEditModeTestYieldInstruction` (`EnterPlayMode`, `ExitPlayMode`, `RecompileScripts`, `WaitForDomainReload`) is not a `YieldInstruction` and exempts the method. A setup that enters Play Mode or recompiles scripts stays a coroutine.
- The analyzer does not try to detect the two situations in the notes at the top: whether a test in the fixture reloads the domain is a property of the test body, not of the setup method, and whether the rewritten method depends on a coexisting `[SetUp]` method is not visible from the signature. Both are verified against `TestCommandBuilder`, `SetUpTearDownCommand`, and `EnumerableSetUpTearDownCommand` in Unity Test Framework 1.6.0: `TestCommandBuilder` wraps the test in `SetUpTearDownCommand` (`[SetUp]` and `[TearDown]`), then in the attributes implementing `IWrapSetUpTearDown`, then in `EnumerableSetUpTearDownCommand` (`[UnitySetUp]` and `[UnityTearDown]`), so the coroutine-style methods also run outside any `IWrapSetUpTearDown` wrapper; `EnumerableSetUpTearDownCommand` keeps its progress in `UnityTestExecutionContext.SetUpTearDownState`, which survives a domain reload, while `SetUpTearDownCommand` starts from a fresh state every time.
- Where a coroutine-style setup or teardown is kept for either reason, or by choice, suppress the diagnostic at that method with `#pragma warning disable UTF4007`.
- `async Task` setup and teardown methods have limitations of their own that a migrated method must respect: an unbounded wait needs a time limit (UTF4002), and `async void` is invoked but never awaited (UTF1007).

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF4007.severity = suggestion
```
