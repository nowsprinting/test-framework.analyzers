# UTF1006 — Only Task is supported as an async test method return type

Detects a test method that has the `async` modifier or an awaitable return type, and whose return type is not `System.Threading.Tasks.Task`. Unity Test Framework runs only `Task` (non-generic) as an async test. Every other return type, such as `UniTask`, `UniTaskVoid`, `Awaitable`, or `ValueTask`, is run through NUnit's synchronous command and fails before the test body completes.

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported as an async test method return type: the test fails without running. Return 'Task' instead."

`{0}` is the declared return type, e.g. `UniTask`.

Severity is Error because the test cannot succeed: depending on the `async` modifier, NUnit either marks the method as not runnable when it is loaded, or throws `NullReferenceException` from its own async adapter as soon as the test method returns. The test body is never run to completion under the test runner.

## Motivation

Unity Test Framework decides how to run a test method from its exact return type, as described in [UTF1002](UTF1002.md). Only `Task` (non-generic) is routed to `TaskTestMethodCommand`. Every other return type falls through to `UnityTestMethodCommand`, which inherits NUnit's synchronous `TestMethodCommand`. What happens there depends on whether the method has the `async` modifier:

- **With the `async` modifier** (`async UniTask`, `async UniTaskVoid`, `async Awaitable`): the compiler marks the method with `AsyncStateMachineAttribute`, so NUnit treats it as an async method and invokes it through `AsyncInvocationRegion`. `AsyncTaskInvocationRegion.WaitForPendingOperationsToComplete` looks up a parameterless `Wait` method on the returned object by reflection and invokes it (NUnit 3.5 source, on which the bundled Custom NUnit 2.0.5 is based; the `"Wait"` literal is present in the bundled assembly). None of these types has such a method, so the lookup returns `null` and the test is recorded as an error with `NullReferenceException` and no further explanation. The test body has already run up to its first `await`; the continuation runs a few frames later, outside any test case, and an assertion failure in it is logged as an unhandled exception instead of being attributed to the test.
- **Without the `async` modifier** (`UniTask Foo() => ...`): NUnit treats the method as a synchronous method with a non-void return type and marks it as not runnable when it is loaded, with the message "Method has non-void return value, but no result is expected". The test body never runs.

Neither outcome freezes the Editor, unlike `Task<TResult>` with `ExpectedResult` (UTF1002), but neither runs the test either. Verified with the NUnit build bundled with Unity Test Framework 1.6.0 (Unity 6000.4) and UniTask 2.5.11: `async UniTask`, `async UniTaskVoid`, `async Awaitable`, and non-async `UniTask`.

The supported pattern is to return `Task`. Awaiting a `UniTask`, `Awaitable`, or any other awaitable inside an `async Task` test method is fine; only the return type of the test method itself matters.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers checks the return type of a `[Test]` or `[TestCase]` method in `TestMethodUsageAnalyzer` as follows: an `async void` method is reported by NUnit1012; otherwise, if the return type is awaitable (it has a `GetAwaiter()` method whose return type implements `INotifyCompletion` with `IsCompleted` and `GetResult()`), the method is accepted as long as `GetResult()` returns `void`, and NUnit1013 is reported only when `GetResult()` returns a value; a non-awaitable, non-void return type is reported by NUnit1007. NUnit itself accepts any awaitable return type, so this is correct for NUnit but not for Unity Test Framework, which supports only `Task`.

Consequently, `UniTask` and `Awaitable` pass NUnit.Analyzers without a diagnostic, with or without the `async` modifier. `UniTaskVoid` happens to be reported by NUnit1007 because it has no `GetAwaiter()` method, but the message talks about `ExpectedResult` and does not point at the actual defect. `[TestCaseSource]` methods are not inspected by any of these rules. This rule rejects every return type other than `Task` on all three attributes. Verified with NUnit.Analyzers 3.9.0 (the version bundled with this package) by running it, and with 4.15.0 by reading its source.

## Bad

```csharp
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;

public class MyTest
{
    [Test]   // UTF1006 (not reported by NUnit.Analyzers); NullReferenceException in NUnit's async adapter
    public async UniTask AwaitsUniTask()
    {
        await UniTask.NextFrame();
        Assert.That(true, Is.True);   // runs after the test has already failed, outside any test case
    }

    [Test]   // UTF1006 (not reported by NUnit.Analyzers); NullReferenceException in NUnit's async adapter
    public async Awaitable AwaitsAwaitable()
    {
        await Awaitable.NextFrameAsync();
        Assert.That(true, Is.True);
    }

    [Test]   // UTF1006 (not reported by NUnit.Analyzers); not runnable, fails at load time
    public UniTask ReturnsUniTask()
    {
        return RunAsync();
    }

    [Test]   // UTF1006 (also NUnit1007); NullReferenceException in NUnit's async adapter
    public async UniTaskVoid AwaitsUniTaskVoid()
    {
        await UniTask.NextFrame();
    }

    private static async UniTask RunAsync()
    {
        await UniTask.NextFrame();
    }
}
```

## Good

```csharp
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;

public class MyTest
{
    [Test]
    public async Task AwaitsUniTask()
    {
        await UniTask.NextFrame();   // awaiting a UniTask inside an async Task test method is fine
        Assert.That(true, Is.True);
    }

    [Test]
    public async Task AwaitsAwaitable()
    {
        await Awaitable.NextFrameAsync();
        Assert.That(true, Is.True);
    }

    [TestCase(1, ExpectedResult = 2)]   // synchronous test methods may return a value
    public int IncrementSync(int value)
    {
        return value + 1;
    }
}
```

## Notes

- The rule matches any method marked with `TestAttribute`, `TestCaseAttribute`, or `TestCaseSourceAttribute` that either has the `async` modifier or has an awaitable return type, and whose return type is none of `void`, `Task`, and `Task<TResult>`. The diagnostic is reported once per method, at the return type, regardless of how many test attributes are applied to the method.
- Only `TestAttribute`, `TestCaseAttribute`, and `TestCaseSourceAttribute` themselves are matched; attributes derived from them are not detected. Attributes inherited from an overridden base method are not inspected either, so an override that relies on the base declaration for its attribute is not reported.
- "Async test method" is used here in NUnit's sense: a method with the `async` modifier, or one whose return type is awaitable. A return type is awaitable when it declares an instance `GetAwaiter()` method that follows the awaiter pattern, the same criterion NUnit.Analyzers uses. An extension-method `GetAwaiter` is not resolved, so a non-async method returning such a type is not reported.
- Whether `ExpectedResult` is specified does not affect the diagnostic; Unity Test Framework routes by return type only.
- `async void` is out of scope; NUnit1012 reports it, and NUnit marks the method as not runnable at load time with the message "Async test method must have non-void return type".
- `Task<TResult>` is out of scope; UTF1002 reports it.
- A non-async method whose return type is neither awaitable nor `void`, such as `UniTaskVoid Foo()` without the `async` modifier, is out of scope; NUnit1007 reports it.
- Coroutine-style test methods with `[UnityTest]` are out of scope. `UnityTestAttribute` marks a method whose return type is not `IEnumerator` as not runnable with its own message.
- `ValueTask` is matched through the same criteria and is expected to fail in the same way, but only `UniTask`, `UniTaskVoid`, and `Awaitable` have been verified.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF1006.severity = warning
```
