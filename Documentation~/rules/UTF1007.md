# UTF1007 — Only Task is supported as an async SetUp and TearDown method return type

Detects a method marked with `SetUpAttribute` or `TearDownAttribute` that has the `async` modifier or an awaitable return type, and whose return type is not `System.Threading.Tasks.Task`. Unity Test Framework awaits only `Task`-returning setup and teardown methods. An `async void` method is invoked but never awaited, so the test body runs before the setup completes. Every other return type, such as `Task<TResult>`, `UniTask`, `UniTaskVoid`, or `Awaitable`, makes NUnit mark the whole fixture as not runnable, so every test in it fails without running.

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported as an async SetUp or TearDown method return type: the method is not awaited or the fixture fails. Return 'Task' instead."

`{0}` is the declared return type, e.g. `void` or `UniTask`.

Severity is Error because no test in the fixture can be trusted: with `async void`, every test runs against a setup that has not finished and a teardown that has not finished, and any exception thrown after the first `await` is lost; with any other return type, every test in the fixture is reported as failed without running.

## Motivation

Unity Test Framework replaces NUnit's per-test setup and teardown command with its own `SetUpTearDownCommand`, which collects `[SetUp]` and `[TearDown]` methods whose return type is exactly `void` or exactly `Task`. A `Task`-returning method is polled from a coroutine until it completes (supported since Unity Test Framework 1.3.0). A `void`-returning method is invoked synchronously.

Before that, NUnit validates the signature of every `[SetUp]` and `[TearDown]` method when the fixture is built, and accepts only `void` and `Task` as the return type. What happens with any other signature depends on the return type:

- **`async void`**: passes NUnit's validation because the return type is `void`, and Unity Test Framework invokes it as a synchronous method. The call returns at the first `await`, and nothing waits for the rest. For a synchronous test method, `ImmediateEnumerableCommand` runs the setup, the test body, and the teardown in the same frame, so the test body always observes the state before the first `await`. The continuation runs after the test has finished, outside any test case. An exception thrown there is logged as an unhandled exception instead of being attributed to the test, and it can fail whichever test happens to be running at that time. Whether a continuation happens to complete before the test body depends on the kind of test method and on what is awaited; it is never guaranteed.
- **Any other return type** (`Task<TResult>`, `UniTask`, `UniTaskVoid`, `Awaitable`, with or without the `async` modifier): fails NUnit's validation. The fixture is marked as not runnable with the message "Invalid signature for SetUp or TearDown method: &lt;method name&gt;", and every test in it is reported as failed with that message without running.

Verified with the NUnit build bundled with Unity Test Framework 1.6.0 (Unity 6000.4) and UniTask 2.5.11: `async void`, `async UniTask`, `async UniTaskVoid`, `async Task<int>`, and `async Awaitable`.

The supported pattern is to return `Task`. Awaiting a `UniTask`, `Awaitable`, or any other awaitable inside an `async Task` setup or teardown method is fine; only the return type of the method itself matters. A `[UnitySetUp]` or `[UnityTearDown]` coroutine is the alternative when yield instructions are needed.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule that inspects the return type or the `async` modifier of a `[SetUp]` or `[TearDown]` method. The rules that look at setup and teardown methods are NUnit1026, which checks accessibility, and NUnit1032, NUnit3002, and NUnit3004, which follow field initialization and disposal inside the method bodies. NUnit1012 and NUnit1013, which report `async void` and wrong `Task` shapes, inspect only test methods. Verified with NUnit.Analyzers 3.9.0 (the version bundled with this package) by running it, and with 4.15.0 by reading its source; the `.editorconfig` options added in 4.11 only let users register additional setup and teardown method names and add no signature check.

## Bad

```csharp
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    private bool _ready;

    [SetUp]   // UTF1007; invoked but not awaited, the test body runs before _ready is set
    public async void SetUp()
    {
        await UniTask.NextFrame();
        _ready = true;
    }

    [TearDown]   // UTF1007; the fixture is not runnable, every test fails without running
    public async UniTask TearDown()
    {
        await UniTask.NextFrame();
    }

    [SetUp]   // UTF1007; reported even without the async modifier, the fixture is not runnable
    public Task<int> SetUpWithResult()
    {
        return Task.FromResult(0);
    }

    [Test]
    public void MyTestMethod()
    {
        Assert.That(_ready, Is.True);
    }
}
```

## Good

```csharp
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _ready;

    [SetUp]
    public async Task SetUp()
    {
        await UniTask.NextFrame();   // awaiting a UniTask inside an async Task setup method is fine
        _ready = true;
    }

    [TearDown]   // synchronous methods are fine
    public void TearDown()
    {
        _ready = false;
    }

    [UnityTearDown]
    public IEnumerator UnityTearDown()
    {
        yield return null;
    }

    [Test]
    public void MyTestMethod()
    {
        Assert.That(_ready, Is.True);
    }
}
```

## Notes

- The rule matches any method marked with `SetUpAttribute` or `TearDownAttribute` that either has the `async` modifier or has an awaitable return type, and whose return type is not `Task`. The diagnostic is reported once per method, at the return type, even when both attributes are applied to the method.
- Only `SetUpAttribute` and `TearDownAttribute` themselves are matched; attributes derived from them are not detected. Attributes inherited from an overridden base method are not inspected either, so an override that relies on the base declaration for its attribute is not reported.
- "Async" is used here in NUnit's sense: a method with the `async` modifier, or one whose return type is awaitable. A return type is awaitable when it declares an instance `GetAwaiter()` method that follows the awaiter pattern. An extension-method `GetAwaiter` is not resolved, so a non-async method returning such a type is not reported.
- A non-async method whose return type is neither awaitable nor `void`, such as `int SetUp()`, is out of scope. NUnit rejects it with the same "Invalid signature" message, but that is an NUnit signature rule rather than a Unity Test Framework limitation.
- `ConfigureAwait(false)` does not exempt the method; the rule is signature-based and does not inspect the awaits.
- `[OneTimeSetUp]` and `[OneTimeTearDown]` methods are out of scope; UTF1004 reports them.
- `[UnitySetUp]`, `[UnityTearDown]`, `[UnityOneTimeSetUp]`, and `[UnityOneTimeTearDown]` methods whose return type is not `IEnumerator` are out of scope; UTF1009 reports them.
- `ValueTask` is matched through the same criteria and is expected to fail in the same way, but only `void`, `Task<TResult>`, `UniTask`, `UniTaskVoid`, and `Awaitable` have been verified.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF1007.severity = warning
```
