# UTF4001 — Test methods that wait for a condition must have a Timeout attribute

Detects a test method that waits for a condition with no time limit of its own, when neither the method, its containing type, nor the assembly has a `Timeout` attribute. Two shapes are recognized: a `while` or `do` loop that yields or awaits in its body, and a call to a predicate-wait API (`WaitUntil`, `WaitWhile`, and the `UniTask.WaitUntil` family). When the condition never holds, such a test runs until the 180-second default timeout of Unity Test Framework.

| Item     | Value     |
|----------|-----------|
| Category | Style     |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' waits for a condition without a time limit: the test runs for 180 seconds when the condition never holds. Apply a Timeout attribute with a short value to the test method."

`{0}` is the construct that waits: `while` or `do` for a loop, the name of the invoked API, e.g. `WaitUntil`, `WaitWhile`, `UniTask.WaitUntil`, `UniTask.WaitUntilValueChanged`, or the name of a helper method in the same compilation that waits inside, e.g. `WaitForLanding`.

The diagnostic is reported at each waiting construct in the test method: the `while` or `do` keyword of the loop (also when the loop is inside a lambda or a local function declared in the test method), the `new WaitUntil(...)` / `new WaitWhile(...)` object creation, the `UniTask.WaitUntil(...)` invocation, or the invocation of a helper method that waits. A method with several waits gets one diagnostic per wait.

Helpers are followed to a bounded depth. The test method body is depth 0. An invocation that is the operand of `await` or `yield return` and resolves to a method with a body in the same compilation is walked at depth + 1, and a lambda or local function declared in the body being walked is walked at depth + 1 as well. Bodies at depth 3 and deeper are not walked.

Severity is Error because the test must not be run without a time limit. At Warning or below, a test that never reaches its condition would be run and would occupy the Editor or the player for three minutes per attempt.

## Motivation

A test that drives a state transition and then waits for it is written as a wait loop or with a predicate-wait API:

```csharp
while (!_grounded) yield return null;
await UniTask.WaitUntil(() => _grounded);
```

When the code under test works, the condition holds within a few frames. When it does not, because of a bug or because the feature is not implemented yet in a test-first cycle, nothing in the test ever ends the wait. Unity Test Framework then ends the test by its default timeout: `UnityWorkItem.k_DefaultTimeout` is `1000 * 180` milliseconds, present since at least version 1.1.33 and unchanged in 1.6.0. The limit is enforced by `TimeoutCommand` for coroutine-style test methods and by `TaskTestMethodCommand` for `async Task` test methods (verified against Unity Test Framework 1.6.0 source), so the wait does end, but only after three minutes. In a red-green cycle every red run of such a test stalls the run for three minutes, and a test suite with several of them stalls for the sum.

NUnit's `TimeoutAttribute` (`NUnit.Framework.TimeoutAttribute`, [Timeout](https://docs.nunit.org/articles/nunit/writing-tests/attributes/timeout.html)) replaces the default with a value in milliseconds. A few seconds is enough for a transition that completes within frames, so a failing test is reported within seconds instead of minutes. The attribute is declared `AttributeUsage(AttributeTargets.Method | AttributeTargets.Class | AttributeTargets.Assembly, AllowMultiple = false, Inherited = false)` in NUnit 3.5, which `com.unity.ext.nunit` 2.0.5 is based on; the method-level value takes precedence over the class-level one, and both over the assembly-level one.

### Why the analyzer recognizes unbounded waits instead of excluding bounded ones

Most `await` and `yield return` statements in a test are bounded by construction: `await UniTask.Delay(1000)`, `await UniTask.NextFrame()`, `await UniTask.DelayFrame(5)`, `await Task.Yield()`, `yield return new WaitForSeconds(1f)`, `yield return SceneManager.UnloadSceneAsync(scene)`, and every `UnityEngine.Awaitable` factory method complete after a fixed time, a fixed number of frames, or a finite engine operation. Listing all of them as exclusions would need an allow list that grows with every library and every project.

The rule takes the opposite approach and recognizes only the two shapes that are unbounded by construction:

1. A `while` or `do` loop whose body contains `yield return` or `await`. The loop ends only when its condition changes, and the yield or await inside is what lets frames advance while it waits. `for` and `foreach` loops are treated as bounded.
2. A call to an API whose completion depends on a predicate supplied by the test: `UnityEngine.WaitUntil` and `UnityEngine.WaitWhile` created with the single-argument constructor, and `Cysharp.Threading.Tasks.UniTask.WaitUntil`, `UniTask.WaitWhile` (including the `<T>(T state, Func<T, bool> predicate, ...)` overloads), `UniTask.WaitUntilValueChanged`, and `UniTask.WaitUntilCanceled` (verified against UniTask 2.5.11).

Everything else is never reported, so no allow list and no per-project configuration are needed. The `WaitUntil` and `WaitWhile` constructors that take a `TimeSpan timeout` (verified against the Unity 6000.4 Script Reference) end by themselves and are not reported.

A wait is often factored out of the test method into a private helper (`yield return WaitForLanding();`) or a lambda. The rule follows `await` and `yield return` into helper methods of the same compilation and into lambdas and local functions, two levels deep, so that the common one- and two-level factoring is still caught. The walk is bounded, as in UTF5001, because an unbounded walk over an arbitrary call graph is too expensive for an analyzer that runs on every keystroke.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule about `TimeoutAttribute`. On a regular .NET test host a test is run on a worker thread and a stuck test blocks only that thread, and NUnit itself has no default timeout, so there is nothing for it to report.

## Bad

```csharp
using System;
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _grounded;

    [UnityTest]
    public IEnumerator LoopInCoroutine()
    {
        StartLanding();
        while (!_grounded)   // UTF4001; the loop never ends when the flag is never set
        {
            yield return null;
        }
        Assert.That(_grounded, Is.True);
    }

    [UnityTest]
    public IEnumerator WaitUntilInCoroutine()
    {
        StartLanding();
        yield return new WaitUntil(() => _grounded);   // UTF4001
        Assert.That(_grounded, Is.True);
    }

    [Test]
    public async Task LoopInAsync()
    {
        StartLanding();
        do
        {
            await UniTask.NextFrame();
        } while (!_grounded);   // UTF4001; reported at 'do'
        Assert.That(_grounded, Is.True);
    }

    [Test]
    public async Task UniTaskWaitUntilInAsync()
    {
        StartLanding();
        await UniTask.WaitUntil(() => _grounded);   // UTF4001
        Assert.That(_grounded, Is.True);
    }

    [UnityTest]
    public IEnumerator LoopInHelper()
    {
        StartLanding();
        yield return WaitForLanding();   // UTF4001; the helper loops until the flag is set (depth 1)
        Assert.That(_grounded, Is.True);
    }

    [Test]
    public async Task LoopInNestedHelper()
    {
        StartLanding();
        await WaitForLandingAsync();   // UTF4001; the helper awaits another helper that loops (depth 2)
        Assert.That(_grounded, Is.True);
    }

    [Test]
    public async Task LoopInLambda()
    {
        StartLanding();
        Func<UniTask> waitForLanding = async () =>
        {
            while (!_grounded)   // UTF4001; reported at the loop inside the lambda (depth 1)
            {
                await UniTask.NextFrame();
            }
        };
        await waitForLanding();
        Assert.That(_grounded, Is.True);
    }

    private IEnumerator WaitForLanding()
    {
        while (!_grounded)
        {
            yield return null;
        }
    }

    private async UniTask WaitForLandingAsync()
    {
        await PollAsync();
    }

    private async UniTask PollAsync()
    {
        while (!_grounded)
        {
            await UniTask.NextFrame();
        }
    }

    private void StartLanding()
    {
        // Sets _grounded from a coroutine or Update several frames later
    }
}
```

## Good

```csharp
using System.Collections;
using System.Threading.Tasks;
using Cysharp.Threading.Tasks;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.SceneManagement;
using UnityEngine.TestTools;

public class MyTest
{
    private bool _grounded;

    [UnityTest]
    [Timeout(5000)]   // the test fails after five seconds when the flag is never set
    public IEnumerator LoopInCoroutine()
    {
        StartLanding();
        while (!_grounded)
        {
            yield return null;
        }
        Assert.That(_grounded, Is.True);
    }

    [Test]
    [Timeout(5000)]
    public async Task UniTaskWaitUntilInAsync()
    {
        StartLanding();
        await UniTask.WaitUntil(() => _grounded);
        Assert.That(_grounded, Is.True);
    }

    [Test]
    public async Task BoundedWaits()   // nothing here waits for a condition, no Timeout needed
    {
        await UniTask.Delay(1000);
        await UniTask.NextFrame();
        await UniTask.DelayFrame(5);
        await Task.Yield();
        for (var i = 0; i < 10; i++)
        {
            await UniTask.Yield();
        }
    }

    [UnityTest]
    public IEnumerator BoundedYields()
    {
        yield return new WaitForSeconds(1f);
        yield return SceneManager.UnloadSceneAsync("Stage");
    }

    private void StartLanding()
    {
        // Sets _grounded from a coroutine or Update several frames later
    }
}
```

## Notes

- A test method is recognized the way NUnit builds tests: a method with an attribute implementing `ITestBuilder` or `ISimpleTestBuilder` (`[Test]`, `[UnityTest]`, `[TestCase]`, and user-defined builders). Waits in `[UnitySetUp]`, `[UnityTearDown]`, and other non-test methods are not reported.
- The rule is satisfied by a `Timeout` attribute on the test method, declared on its containing type, or applied to the assembly; the method-level value takes precedence over the class-level one, and both over the assembly-level one. Each of the following is therefore not reported, and each is a test case of the analyzer:

  ```csharp
  [Timeout(5000)]   // class level: covers every test method declared in the fixture
  public class MyTest
  {
      [UnityTest]
      public IEnumerator LoopInCoroutine() { while (!_grounded) yield return null; }
  }
  ```

  ```csharp
  [assembly: Timeout(5000)]   // assembly level: covers every test method in the assembly, in any file

  public class MyTest
  {
      [UnityTest]
      public IEnumerator LoopInCoroutine() { while (!_grounded) yield return null; }
  }
  ```

  The attribute is declared `Inherited = false`, so a `Timeout` on a base class is not recognized; apply it to the derived fixture, the method, or the assembly.
- Only the presence of the attribute is checked, not its value. A test that waits for a transition that completes within frames needs only a few seconds; the rule does not enforce a maximum.
- Helpers are followed only through `await` and `yield return` operands (`await WaitForReadyAsync();`, `yield return WaitForReady();`), only when the helper has a body in the same compilation, and only two levels deep. A wait at depth 3 (a helper of a helper of a helper), a helper in another assembly, a helper invoked without `await` or `yield return` (`yield return StartCoroutine(WaitForReady());`), and a lambda passed in from outside the test method are not seen through. Apply `Timeout` to such tests yourself.
- A lambda or local function declared in a walked body is walked whether or not it is invoked, so a loop in a lambda that is stored but never called is still reported.
- Awaiting a `Task`, `UniTask`, or `Awaitable` returned by other code is never reported, including `TaskCompletionSource.Task`, `UniTaskCompletionSource.Task`, and UniTask async events, because the analyzer cannot know whether the awaited operation is bounded.
- A synchronous busy loop (`while (!ready) { }`) is out of scope: it never returns control to the test runner, so no `Timeout` can interrupt it.
- A `while` loop with a counter (`while (n-- > 0) yield return null;`) is reported although it is bounded. Write it as a `for` loop.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF4001.severity = warning
```
