# UTF1005 — Attributes implementing ICommandWrapper are not supported on async and coroutine-style test methods

Detects a test method whose return type is `System.Threading.Tasks.Task` or `System.Collections.IEnumerator` and that is marked with an attribute implementing `NUnit.Framework.Interfaces.ICommandWrapper` (the base interface of `IWrapTestMethod` and `IWrapSetUpTearDown`). Unity Test Framework runs such methods through its own coroutine-driven commands, and a command produced by a user-defined wrapper cannot drive them. The test never runs its body: it is recorded as a failure or an error at run time.

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported on async and coroutine-style test methods: the test fails without running. Apply it to synchronous test methods only."

`{0}` is the unqualified type name of the offending attribute, including the `Attribute` suffix (for example, `MyWrapperAttribute`). When a derived attribute is applied, the derived type is named.

Severity is Error because the test cannot succeed: depending on the combination, Unity Test Framework either replaces the test with a failing command before it starts, or throws `NotImplementedException` from the command chain and records it as a test error. The test body is never executed in either case.

## Motivation

NUnit lets a custom attribute alter test execution by implementing `IWrapTestMethod` or `IWrapSetUpTearDown` ([ICommandWrapper interface](https://docs.nunit.org/articles/nunit/extending-nunit/ICommandWrapper-Interface.html)). The attribute's `Wrap` method returns a `TestCommand` whose synchronous `Execute` calls the inner command's `Execute`. Unity Test Framework documents this pattern for Unity: the [Actions outside of tests](https://docs.unity3d.com/Manual/test-framework/reference-actions-outside-tests.html) page lists both interfaces in the execution order and states that "the list of actions is the same for both `Test` and `UnityTest`", and the course section "16. Custom attributes" (with sample `16_CustomAttributes_Solution`) walks through writing an `IWrapTestMethod` attribute whose command overrides only `Execute`. Both give the impression that such an attribute works on any test method. It works only on synchronous test methods.

Unity Test Framework does not run `async Task` and coroutine-style test methods through NUnit's synchronous `Execute`. `TestCommandBuilder.BuildTestCommand` builds `TaskTestMethodCommand` for a `Task`-returning method and `EnumerableTestMethodCommand` for an `IEnumerator`-returning method. Both implement the internal interface `IEnumerableTestMethodCommand`, whose `ExecuteEnumerable` yields once per frame, and both throw `NotImplementedException("Use ExecuteEnumerable")` from `Execute`. The commands in the chain built by `BuildTestCommand`, such as `TestActionCommand`, check whether their inner command implements `IEnumerableTestMethodCommand` and fall back to `Execute` when it does not. `IEnumerableTestMethodCommand` is `internal` and undocumented, so a user-defined command cannot implement it, and a user-defined wrapper always breaks the chain. What happens next depends on the combination (verified against Unity Test Framework 1.4.6 and 1.6.0):

- **`IWrapTestMethod` on a `Task`-returning method**: `BuildTestCommand` performs no check for this combination. At run time, `TestActionCommand` sees a non-enumerable inner command and calls its `Execute`, which reaches `TaskTestMethodCommand.Execute` and throws `NotImplementedException`. `UnityLogCheckDelegatingCommand` captures the exception and records it as a test error. The wrapper's code before the inner call runs; the test body never does.
- **`IWrapTestMethod` on an `IEnumerator`-returning method**, and **`IWrapSetUpTearDown` on either kind**: `BuildTestCommand` detects that the wrapped command is not enumerable and replaces the whole test with a `FailCommand`. Its message names the wrapper attribute and the test builder attribute on the method (`TestAttribute`, `UnityTestAttribute`, `TestCaseAttribute`, and so on): "'MyWrapperAttribute' is not supported on TestAttribute as it does not handle returning IEnumerator." The "returning IEnumerator" wording is used for `Task`-returning methods too, which is misleading. The check for `IWrapSetUpTearDown` on `Task`-returning methods was added in Unity Test Framework 1.4.5 (DSTR-1040); before that, the combination failed at run time.

The built-in NUnit attributes `RepeatAttribute`, `RetryAttribute`, and `MaxTimeAttribute` are also command wrappers, but Unity Test Framework recognizes the commands they produce by exact type name (`TryReplaceWithEnumerableCommand`) and substitutes its own enumerable implementations, so they work on async and coroutine-style test methods. `ParametrizedIgnoreAttribute`, provided by Unity Test Framework, produces an internal command that implements `IEnumerableTestMethodCommand`. No such substitution exists for user-defined wrappers, and there is no public API for a user-defined command to take part in the coroutine-driven chain. A user-defined wrapper attribute can be applied only to synchronous test methods.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers has no rule that inspects attributes implementing `ICommandWrapper`, `IWrapTestMethod`, or `IWrapSetUpTearDown`. The rules that look at async test methods (NUnit1012, NUnit1013, NUnit1014) check only the method's return type against `ExpectedResult`, and no rule is aware of `IEnumerator`-returning test methods, which are a Unity Test Framework extension. Verified with NUnit.Analyzers 3.9.0.

## Bad

```csharp
using System.Collections;
using System.Threading.Tasks;
using NUnit.Framework;
using NUnit.Framework.Interfaces;
using NUnit.Framework.Internal;
using NUnit.Framework.Internal.Commands;
using UnityEngine.TestTools;

public class MyWrapperAttribute : NUnitAttribute, IWrapTestMethod
{
    public TestCommand Wrap(TestCommand command)
    {
        return new MyCommand(command);
    }
}

public class MyCommand : DelegatingTestCommand
{
    public MyCommand(TestCommand innerCommand) : base(innerCommand)
    {
    }

    public override TestResult Execute(ITestExecutionContext context)
    {
        return innerCommand.Execute(context);
    }
}

public class MyTest
{
    [Test]
    [MyWrapper]   // UTF1005; NotImplementedException is recorded as a test error, the test body never runs
    public async Task AsyncTest()
    {
        await Task.Yield();
    }

    [UnityTest]
    [MyWrapper]   // UTF1005; the test is replaced with a failing command before it starts
    public IEnumerator CoroutineTest()
    {
        yield return null;
    }
}
```

## Good

```csharp
using System.Collections;
using System.Threading.Tasks;
using NUnit.Framework;
using UnityEngine.TestTools;

public class MyTest
{
    [Test]
    [MyWrapper]   // synchronous test methods are fine (MyWrapperAttribute is defined in the Bad example)
    public void SyncTest()
    {
    }

    [Test]
    [Repeat(3)]   // Unity Test Framework replaces the command produced by Repeat
    public async Task RepeatedAsyncTest()
    {
        await Task.Yield();
    }

    [UnityTest]
    [Retry(3)]   // Unity Test Framework replaces the command produced by Retry
    public IEnumerator RetriedCoroutineTest()
    {
        yield return null;
    }

    [UnityTest]
    [MaxTime(1000)]   // Unity Test Framework replaces the command produced by MaxTime
    public IEnumerator MaxTimeCoroutineTest()
    {
        yield return null;
    }

    [Test]
    [ParametrizedIgnore("b", 10)]   // ParametrizedIgnore is provided by Unity Test Framework and handles async tests
    public async Task ParametrizedIgnoreAsyncTest([Values("a", "b")] string someString, [Values(5, 10)] int someInt)
    {
        await Task.Yield();
    }
}
```

## Notes

- The rule matches a method that carries an attribute implementing `ITestBuilder` or `ISimpleTestBuilder` (such as `TestAttribute`, `UnityTestAttribute`, `TestCaseAttribute`, or `TestCaseSourceAttribute`), whose return type is exactly `System.Threading.Tasks.Task` or `System.Collections.IEnumerator`, and that also carries an attribute whose type implements `NUnit.Framework.Interfaces.ICommandWrapper`. Unity Test Framework reads wrapper attributes only from test methods, so a wrapper on a `[SetUp]`, `[UnitySetUp]`, or other non-test method is inert and out of scope.
- The return type conditions mirror Unity Test Framework: it treats a method as an async test only when the return type is exactly `Task`, and as a coroutine only when it is exactly `IEnumerator`. `Task<TResult>` is covered by UTF1002. The `async` modifier alone does not matter; `async void` test methods are reported by NUnit1012.
- The wrapper attribute is matched through the interfaces implemented by its type, so attributes derived from a wrapper attribute and attributes defined in other assemblies are detected.
- The following attributes are exempt because Unity Test Framework handles the commands they produce. The exemption is by exact type; an attribute derived from one of them is reported. Unity Test Framework substitutes commands by exact type name, so a derived attribute that overrides `Wrap` to return its own command does fail at run time, whereas one that does not override `Wrap` works and is a false positive of this rule.
  - `NUnit.Framework.RepeatAttribute`
  - `NUnit.Framework.RetryAttribute`
  - `NUnit.Framework.MaxTimeAttribute` (supported on async and coroutine-style test methods since Unity Test Framework 1.4.5)
  - `UnityEngine.TestTools.ParametrizedIgnoreAttribute`
- `TimeoutAttribute` and `PerformanceAttribute` (Unity Performance Testing package) are not command wrappers and are never reported.
- Wrapper attributes applied at class or assembly level are ignored by Unity Test Framework and are out of scope. Attributes inherited from a base-class virtual method are not detected; the rule looks only at the attributes written on the method.
- The diagnostic is reported at each offending attribute.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF1005.severity = warning
```
