# UTF2002 — Async delegates are not supported as the actual value of Throws constraints, Assert.Throws, Assert.Catch, and Assert.DoesNotThrow

Detects an async delegate passed as the actual value of a `Throws` constraint (`Assert.That(async () => ..., Throws.TypeOf<T>())`), or passed to `Assert.Throws`, `Assert.Catch`, or `Assert.DoesNotThrow`. NUnit waits for the returned `Task` synchronously on the calling thread. Unity Test Framework runs tests on the main thread, so the Editor freezes. The three `TestDelegate` methods fail with an `ArgumentException` instead of freezing, but the fix is the same.

| Item     | Value     |
|----------|-----------|
| Category | Assertion |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "Async delegates are not supported as the actual value of '{0}'. Test the exception with try/catch in an 'async Task' test method instead."

`{0}` is the API that receives the delegate: the `Throws` member that starts the constraint expression for `Assert.That` (e.g. `Throws.TypeOf`, `Throws.InstanceOf`, `Throws.Exception`, `Throws.Nothing`, `Throws.ArgumentException`), or the `Assert` method for `Assert.Throws`, `Assert.Catch`, and `Assert.DoesNotThrow`.

The diagnostic is reported at the delegate argument.

Severity is Error because running the test can freeze the Editor: the returned `Task` is waited on synchronously on the main thread, so any continuation that must run on the main thread never gets scheduled. At Warning or below, the test would be run and the Editor would have to be killed.

## Motivation

The official documentation ([Async tests](https://docs.unity3d.com/Manual/test-framework/reference-async-tests.html)) warns that `Assert.ThrowsAsync` blocks the calling thread and freezes the Editor, and recommends try/catch instead (see UTF2001). The `Throws` constraints share the mechanism, so the natural workaround of switching from `Assert.ThrowsAsync` to `Assert.That(async () => ..., Throws.TypeOf<T>())` freezes in exactly the same way.

The NUnit build bundled with Unity (`com.unity.ext.nunit`, based on NUnit 3.5) decides whether a delegate is asynchronous with `AsyncInvocationRegion.IsAsyncOperation`: the delegate's return type starts with `System.Threading.Tasks.Task`, or its method is marked with `AsyncStateMachineAttribute`. For such a delegate, `AsyncInvocationRegion.Create` returns a region whose `WaitForPendingOperationsToComplete` calls `Task.Wait()` on the calling thread. In Unity that thread is the main thread, and async continuations are posted to `UnitySynchronizationContext`, which is pumped by the main thread. The wait blocks the pump, the continuation never runs, and the Editor freezes. `await Task.Yield()`, `await Task.Delay(...)`, `await Awaitable.NextFrameAsync()`, and awaiting any Unity API are enough to trigger it. This is the same mechanism described in UTF1002 and UTF1004.

The reported APIs reach that wait as follows:

- **`Assert.That(delegate, Throws.*)`**: an async lambda converts to both `TestDelegate` (as `async void`) and `ActualValueDelegate<Task>`; C# overload resolution prefers the delegate with a return type, so `Assert.That<TActual>(ActualValueDelegate<TActual>, IResolveConstraint)` is chosen with `TActual` = `Task`. `ThrowsConstraint` (and `ThrowsNothingConstraint` for `Throws.Nothing`) overrides `ApplyTo(ActualValueDelegate<TActual>)`, wraps the delegate in a `GenericInvocationDescriptor`, and passes it to `ExceptionInterceptor.Intercept`, which detects the async operation and waits on the task. A non-async lambda that returns a `Task` (`() => FooAsync()`) and a method group of a `Task`-returning method take the same path, because the check is on the return type.
- **`Assert.Throws`, `Assert.Catch`, `Assert.DoesNotThrow`**: these accept only `TestDelegate`, so an async lambda becomes `async void`. `AsyncInvocationRegion.Create` rejects it with `ArgumentException` ("'async void' methods are not supported, please use 'async Task' instead"). The Editor does not freeze, but the test fails, and the error text steers the author toward `Assert.ThrowsAsync`, which does freeze (UTF2001). The rule reports these calls with the same message so that the author lands on try/catch directly.

The rule matches on the delegate's shape. Whether a given `Task` actually deadlocks depends on its awaits: a task whose continuations all run off the main thread (for example, with `ConfigureAwait(false)` everywhere) completes, but it still stalls the whole test run for its duration, and the analyzer cannot tell the two apart.

### Why NUnit.Analyzers cannot be used instead

NUnit.Analyzers 3.9.0 has one rule about delegate arguments of exception assertions: NUnit2044 (DelegateRequired) reports passing the *result* of an async call (`Assert.That(FooAsync(), Throws.X)`) instead of a delegate, which is the opposite defect. Later versions add NUnit2057 (DelegateUnnecessary), which explicitly treats an async lambda with a `Throws` constraint as valid, because on a regular .NET test host `Task.Wait()` merely blocks a worker thread. No rule reports an async delegate passed to a `Throws` constraint, since the freeze is specific to Unity's main-thread synchronization context.

## Bad

```csharp
using System;
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public void ThrowsConstraintFreezes()
    {
        Assert.That(async () => await FooAsync(), Throws.TypeOf<InvalidOperationException>());   // UTF2002; freezes the Editor
        Assert.That(() => FooAsync(), Throws.InstanceOf<Exception>().With.Message.Contains("boom"));   // UTF2002; reported even without the async modifier, the delegate returns Task
        Assert.That(BarAsync, Throws.Nothing);   // UTF2002; method group of a Task-returning method
    }

    [Test]
    public void ThrowsRejectsAsyncVoid()
    {
        Assert.Throws<InvalidOperationException>(async () => await FooAsync());   // UTF2002; fails with "'async void' methods are not supported"
    }

    private static async Task FooAsync()
    {
        await Task.Yield();
        throw new InvalidOperationException("boom");
    }

    private static async Task BarAsync()
    {
        await Task.Yield();
    }
}
```

## Good

```csharp
using System;
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [Test]
    public async Task ExceptionIsThrown()
    {
        try
        {
            await FooAsync();
        }
        catch (InvalidOperationException e)
        {
            Assert.That(e.Message, Does.Contain("boom"));
            return;
        }

        Assert.Fail("Expected InvalidOperationException was not thrown");
    }

    [Test]
    public async Task ExceptionIsNotThrown()
    {
        await BarAsync();   // an unexpected exception fails the test by itself
    }

    [Test]
    public void SynchronousDelegatesAreFine()
    {
        Assert.That(() => Foo(), Throws.TypeOf<InvalidOperationException>());
        Assert.Throws<InvalidOperationException>(() => Foo());
    }

    private static async Task FooAsync()
    {
        await Task.Yield();
        throw new InvalidOperationException("boom");
    }

    private static async Task BarAsync()
    {
        await Task.Yield();
    }

    private static void Foo()
    {
        throw new InvalidOperationException("boom");
    }
}
```

## Notes

- A delegate argument is treated as async when any of the following holds, mirroring NUnit's `IsAsyncOperation`:
    - the argument converts to `ActualValueDelegate<TActual>` where `TActual` is `Task` or `Task<TResult>`,
    - the argument is a lambda or anonymous method with the `async` modifier,
    - the argument is a method group whose target method returns `Task` or `Task<TResult>` or has the `async` modifier.
- For `Assert.That`, only constraint expressions that start with a member of `NUnit.Framework.Throws` are matched, including chained expressions such as `Throws.TypeOf<T>().With.Message.EqualTo(...)`. A `Throws` constraint stored in a variable or built from `new ThrowsConstraint(...)` is not detected.
- `Assert.ThrowsAsync`, `Assert.CatchAsync`, and `Assert.DoesNotThrowAsync` are out of scope; UTF2001 reports every call to them.
- Passing the `Task` itself instead of a delegate (`Assert.That(FooAsync(), Throws.X)`) is out of scope; NUnit2044 reports it.
- An async delegate passed to `Assert.That` with a non-`Throws` constraint (`Assert.That(async () => await GetAsync(), Is.EqualTo(1))`) is waited on through the same `Constraint.ApplyTo(ActualValueDelegate<TActual>)` path and also freezes the Editor. It is a separate defect and out of scope for this rule.
- The constraint argument and the delegate argument are located by parameter type (`IResolveConstraint` and a delegate type), not by position, so the message overloads `Assert.That(del, expr, message, args)` and `Assert.Throws(Type, TestDelegate)` are matched the same way as the two-argument forms.
- When the constraint expression starts with a `Throws` property (`Throws.Exception.TypeOf<T>()`), `{0}` is that property (`Throws.Exception`), not the chained member.
- `ValueTask`-returning delegates and delegate types derived from `Task` are not reported; NUnit checks for `Task` and `Task<TResult>` only.
- `ConfigureAwait(false)` does not exempt the delegate; the rule inspects the delegate's shape and does not inspect the awaits.
- `Assert.Throws`, `Assert.Catch`, and `Assert.DoesNotThrow` with an async lambda do not freeze; NUnit fails the test with `ArgumentException` at runtime. They are reported anyway because the correct fix is the same try/catch, not `Assert.ThrowsAsync`.
- Do not write `try { await FooAsync(); Assert.Fail(); } catch (Exception e) { ... }` with a catch-all: it swallows the `AssertionException` thrown by `Assert.Fail`. Catch the expected exception type, or set a flag inside the catch and assert it after the block, as the official documentation shows.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF2002.severity = warning
```
