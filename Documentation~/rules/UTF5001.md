# UTF5001 — ApplyToTest, ApplyToContext, and Wrap must not throw exceptions

Detects an exception that can escape from an implementation of `IApplyToTest.ApplyToTest`, `IApplyToContext.ApplyToContext`, or `ICommandWrapper.Wrap` (the `Wrap` method of `IWrapTestMethod` and `IWrapSetUpTearDown`). The analysis covers `throw` statements and throw expressions in the method body, and follows calls to methods, constructors, and local functions declared in the same compilation. Unity Test Framework invokes these methods outside its exception handling: an exception from `ApplyToTest` replaces the whole fixture with a single not-runnable entry that has no tests, and an exception from `ApplyToContext` on a test method or from `Wrap` aborts the entire test run.

| Item     | Value      |
|----------|------------|
| Category | Extensions |
| Enabled  | True       |
| Severity | Error      |
| CodeFix  | False      |

Message: "'{0}' must not throw exceptions"

`{0}` is the interface member the method implements: `IApplyToTest.ApplyToTest`, `IApplyToContext.ApplyToContext`, or `ICommandWrapper.Wrap`.

Severity is Error because the failure is not confined to one test. With `ApplyToTest`, every test in the fixture is removed from the test tree, including tests that do not carry the attribute; with `ApplyToContext` on a test method or with `Wrap`, the run stops and the remaining tests are not executed.

## Motivation

NUnit lets a custom attribute take part in test discovery and execution through three hooks ([Custom Attributes](https://docs.nunit.org/articles/nunit/extending-nunit/Custom-Attributes.html)): `IApplyToTest.ApplyToTest` modifies the `Test` object while the test tree is built, `IApplyToContext.ApplyToContext` modifies the execution context right before the test runs, and `ICommandWrapper.Wrap` inserts a `TestCommand` into the command chain. Unity Test Framework lists `IApplyToContext`, `IWrapTestMethod`, and `IWrapSetUpTearDown` in the execution order on the [Actions outside of tests](https://docs.unity3d.com/Manual/test-framework/reference-actions-outside-tests.html) page and calls all three hooks from its own runner. Unlike the test method, `SetUp`, `TearDown`, and `ITestAction` callbacks, none of the three is protected by exception handling (verified against Unity Test Framework 1.6.0 and com.unity.ext.nunit 2.0.5 on Unity 6000.4):

- **`ApplyToTest`** is called during test discovery from `Test.ApplyAttributesToTest`, which loops over the attributes without a try/catch. It is reached for attributes on the fixture class (`NUnitTestFixtureBuilder.BuildFrom`), on each test method (`NUnitTestCaseBuilder.BuildTestMethod`), on the suite of a parameterized test method (`DefaultTestCaseBuilder.BuildParameterizedMethodSuite`), and on the assembly (`DefaultTestAssemblyBuilder.BuildTestAssembly`). For the first three, the exception propagates out of the fixture builder to `DefaultSuiteBuilder.BuildFrom`, which catches it and returns a `TestFixture` with `RunState.NotRunnable`, no child tests, and the skip reason "An exception was thrown while loading the test." followed by the exception. The test methods are added to the fixture after the fixture attributes are applied, and the builder stops at the first exception, so a throwing attribute on one test method discards the other test methods of the fixture as well. The Test Runner window shows the fixture as a single not-runnable entry with that reason, no test of the fixture appears in the run result, and nothing appears in the Console. An attribute applied at assembly level makes the whole assembly disappear: the outer catch in `DefaultTestAssemblyBuilder.Build` returns an assembly suite with no children, and `UnityTestAssemblyBuilder` skips assembly suites without children, so not even a not-runnable entry remains.
- **`ApplyToContext`** on a test method is called at run time from `EnumerableApplyChangesToContextCommand.ExecuteEnumerable`, which `TestCommandBuilder.BuildTestCommand` places outside every command of the test itself (only `IgnoreTestCommand` and `StrictCheckCommand` wrap it, and neither catches exceptions), before any of the test's commands start. NUnit's own `ApplyChangesToContextCommand.Execute` wraps the `ApplyChanges` call in a try/catch and records the exception on the test result, so under plain NUnit only that test errors. Unity Test Framework drives the chain through `ExecuteEnumerable` instead of `Execute`, and that path calls `ApplyChanges` without protection. An attribute on the fixture class or on the assembly takes a different path: `CompositeWorkItem` builds its one-time set-up command through NUnit's `CommandBuilder.MakeOneTimeSetUpCommand`, which wraps it in NUnit's `ApplyChangesToContextCommand`, and runs it inside the try/catch of `PerformOneTimeSetUp`. An exception there is recorded as a `OneTimeSetUp` failure of that fixture and the run continues.
- **`Wrap`** is called from `TestCommandBuilder.BuildTestCommand` while the command chain for a test is built, which happens in the work item constructor when the parent suite creates its child work items. Unity Test Framework checks the return value for null and replaces the test with a failing command in that case, but it does not catch exceptions.

An exception from `ApplyToContext` on a test method or from `Wrap` propagates through `DefaultTestWorkItem` (which has only a `finally` block), `CompositeWorkItem`, and `UnityTestAssemblyRunner`, none of which catch it. In the Editor it reaches `TestJobRunner`, which logs the exception, reports "An unexpected error happened while running tests.", and ends the run; in Play Mode, `PlaymodeTestsController` stores the exception and `PlayModeRunTask` rethrows it into the same handler. With `ApplyToContext`, the test that owns the attribute and every test after it are not executed. With `Wrap`, the parent suite builds the command chains of all its children before running the first one, so no test in the fixture is executed, including tests ordered before the one that owns the attribute. In a player build, the runner coroutine terminates with the exception and the run does not complete.

Because all three hooks run before the test body and outside the per-test exception handling, a problem detected in them must be reported through the API instead of thrown: mark the test `NotRunnable` in `ApplyToTest`, and keep `ApplyToContext` and `Wrap` free of operations that can fail. Test discovery instantiates the attribute through `GetCustomAttributes` inside the same `DefaultSuiteBuilder.BuildFrom` try block, so moving the fallible work into the attribute constructor produces the same not-runnable fixture.

### Why existing analyzers cannot be used instead

NUnit.Analyzers has no rule that inspects implementations of `IApplyToTest`, `IApplyToContext`, or `ICommandWrapper`. Verified with NUnit.Analyzers 3.9.0.

The .NET analyzer CA1065 ("Do not raise exceptions in unexpected locations") reports `throw` statements only in a fixed list of members (property getters, event accessors, `Equals`, `GetHashCode`, `ToString`, static constructors, finalizers, `Dispose`, equality operators, and implicit cast operators). The list is not configurable, and the rule does not follow calls into other methods.

## Bad

```csharp
using System;
using NUnit.Framework;
using NUnit.Framework.Interfaces;
using NUnit.Framework.Internal;
using NUnit.Framework.Internal.Commands;

public static class Settings
{
    // Returns null when the key is not set; never throws.
    public static string Get(string key) => Environment.GetEnvironmentVariable(key);
}

public class SettingCommand : DelegatingTestCommand
{
    private readonly string _value;

    public SettingCommand(TestCommand innerCommand, string value) : base(innerCommand)
    {
        _value = value;
    }

    public override TestResult Execute(ITestExecutionContext context)
    {
        TestContext.Out.WriteLine($"Setting: {_value}");
        return innerCommand.Execute(context);
    }
}

public class RequireSettingAttribute : NUnitAttribute, IApplyToTest, IApplyToContext, IWrapTestMethod
{
    private readonly string _key;

    public RequireSettingAttribute(string key)
    {
        _key = key;
    }

    public void ApplyToTest(Test test)
    {
        if (Settings.Get(_key) == null)
        {
            throw new ArgumentException($"Setting '{_key}' is missing");   // UTF5001; the fixture becomes not runnable and all of its tests are lost
        }
    }

    public void ApplyToContext(ITestExecutionContext context)
    {
        context.TestCaseTimeout = ReadTimeout();   // UTF5001; ReadTimeout throws, the test run is aborted
    }

    public TestCommand Wrap(TestCommand command)
    {
        var value = Settings.Get(_key);
        return value != null
            ? new SettingCommand(command, value)
            : throw new InvalidOperationException($"Setting '{_key}' is missing");   // UTF5001; the test run is aborted
    }

    private int ReadTimeout()
    {
        var value = Settings.Get(_key + ".timeout");
        if (value == null)
        {
            throw new InvalidOperationException("Timeout is not set");
        }

        return int.Parse(value);
    }
}
```

## Good

```csharp
using NUnit.Framework;
using NUnit.Framework.Interfaces;
using NUnit.Framework.Internal;
using NUnit.Framework.Internal.Commands;

public class RequireSettingAttribute : NUnitAttribute, IApplyToTest, IApplyToContext, IWrapTestMethod
{
    private const int DefaultTimeout = 30000;
    private readonly string _key;

    public RequireSettingAttribute(string key)
    {
        _key = key;
    }

    // Validation happens here. A NotRunnable test is replaced with a SkipCommand,
    // so ApplyToContext and Wrap are never called for it.
    public void ApplyToTest(Test test)
    {
        if (test.RunState == RunState.NotRunnable || test.RunState == RunState.Ignored)
        {
            return;
        }

        if (Settings.Get(_key) == null || !int.TryParse(Settings.Get(_key + ".timeout"), out _))
        {
            test.RunState = RunState.NotRunnable;
            test.Properties.Set(PropertyNames.SkipReason, $"Setting '{_key}' is missing or invalid");
        }
    }

    // Re-reads the setting with operations that cannot throw. The attribute instance used here
    // is not the one ApplyToTest ran on, so the validated value cannot be kept in a field.
    public void ApplyToContext(ITestExecutionContext context)
    {
        context.TestCaseTimeout = int.TryParse(Settings.Get(_key + ".timeout"), out var timeout) ? timeout : DefaultTimeout;
    }

    public TestCommand Wrap(TestCommand command)
    {
        return new SettingCommand(command, Settings.Get(_key));   // Settings and SettingCommand are defined in the Bad example
    }
}

public class MyTest
{
    [Test]
    [RequireSetting("SERVER_URL")]   // a synchronous test method; see UTF1005 for wrapper attributes on async tests
    public void SyncTest()
    {
    }
}
```

## Notes

- The rule inspects a method that implements `NUnit.Framework.Interfaces.IApplyToTest.ApplyToTest`, `NUnit.Framework.Interfaces.IApplyToContext.ApplyToContext`, or `NUnit.Framework.Interfaces.ICommandWrapper.Wrap`, either implicitly or explicitly, and any override of such a method. The containing type does not have to be an attribute. Where the attribute is applied does not matter; the implementation is inspected on its own.
- A `throw` statement, a throw expression, or a rethrow (`throw;`) in the method body is reported unless it is inside a `try` block in the same method that has a `catch` clause without an exception filter (`when`) whose type is the thrown type or one of its base types, or a general `catch` clause. A `catch` clause with a filter never counts as handling the exception. The thrown type is the static type of the thrown expression.
- Calls to methods, constructors, and local functions whose declaration is in the same compilation are followed transitively, with recursion guarded. A call is reported when an exception escapes from the callee under the same rules, and it is handled by an enclosing `catch` in the caller under the same rules applied to each escaping exception type. Only the statically bound declaration is followed; overrides and other implementations of the callee are not.
- The diagnostic is reported at the `throw` statement or expression when it is in the body of the implementing method, and at the invocation or object creation expression in that body when the exception escapes from a called method. The call site is reported even when the throw is several calls deep.
- Not tracked, and therefore not reported:
  - Methods declared in other assemblies, including NUnit's `Assert` and `Guard`, `int.Parse`, and Unity APIs that throw.
  - Throws inside lambda expressions and anonymous methods, and throws in local functions that are never called from the inspected method.
  - Property accessors, indexers, and operators.
  - Exceptions raised by the runtime, such as `NullReferenceException`.
- Attribute instances are created separately for discovery and for execution: `Test.ApplyAttributesToTest` and `TestCommandBuilder.BuildTestCommand` each call `GetCustomAttributes`, which constructs new instances. A value validated in `ApplyToTest` cannot be passed to `ApplyToContext` or `Wrap` through an instance field; keep constructor arguments as the only state and use non-throwing operations in the other two hooks.
- Only the test-method path of `ApplyToContext` is unprotected. An `IApplyToContext` attribute on the fixture class or on the assembly is applied by NUnit's `CommandBuilder.MakeOneTimeSetUpCommand` inside the try/catch of `CompositeWorkItem.PerformOneTimeSetUp`, so an exception there is recorded as a `OneTimeSetUp` failure of that fixture and the remaining fixtures run. The rule reports the implementation regardless of where the attribute is applied, because the same attribute can be applied to a method.
- The other extension hooks, such as `ITestBuilder.BuildFrom`, `IParameterDataSource.GetData`, and `ITestAction.BeforeTest`, are out of scope. `ITestAction` callbacks are protected by Unity Test Framework's `TestActionCommand`, which records the exception on the test result.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF5001.severity = warning
```
