# UTF1002 — Task<TResult> is not supported as a test method return type

Detects a test method whose return type is `System.Threading.Tasks.Task<TResult>`. Unity Test Framework runs only `Task` (non-generic) as an async test. Without an expected result, NUnit rejects a `Task<TResult>` method at load time; with `ExpectedResult` or `TestCaseData.Returns`, NUnit lets it run, and it is executed synchronously and freezes the Editor.

| Item     | Value     |
|----------|-----------|
| Category | Structure |
| Enabled  | True      |
| Severity | Error     |
| CodeFix  | False     |

Message: "'{0}' is not supported as a test method return type. Return 'Task' and assert the value inside the test method instead of using ExpectedResult."

`{0}` is the declared return type, e.g. `Task<int>`.

Severity is Error because running the test can freeze the Editor: the test body is awaited synchronously on the main thread, so any continuation that must run on the main thread never gets scheduled.

## Motivation

Unity Test Framework decides how to run a test method from its exact return type. Only `Task` (non-generic) is routed to `TaskTestMethodCommand`, which polls the task from a coroutine and lets continuations run on the main thread. Every other return type, including `Task<TResult>`, falls through to `UnityTestMethodCommand`, which inherits NUnit's synchronous `TestMethodCommand`. NUnit runs an async method there by blocking the calling thread until the task completes.

In Unity, async continuations are posted to the main thread via `UnitySynchronizationContext`. When the main thread is blocked waiting for the task, the continuation can never run, and the Editor freezes. `await Task.Yield()`, `await Awaitable.NextFrameAsync()`, and awaiting any Unity API are enough to trigger it. The [official documentation](https://docs.unity3d.com/Manual/test-framework/reference-async-tests.html) describes the same freeze for `Assert.ThrowsAsync` and states that an async test "has return type `Task`".

The usual reason to write `Task<TResult>` is to use `TestCaseAttribute.ExpectedResult` or `TestCaseData.Returns`, because that is what NUnit requires for an async test with an expected result. It does not work in Unity Test Framework because the `Task<TResult>` path freezes. The supported pattern is to return `Task` and assert the value with `Assert.That` inside the method.

### Why NUnit.Analyzers cannot be used instead

NUnit1013 reports `Task<TResult>` on a `[Test]` or `[TestCase]` method when no expected result is given, which incidentally catches the load-time failure. However, NUnit1014 requires `Task<TResult>` as soon as `ExpectedResult` is present, so the combination that actually freezes, `async Task<TResult>` with `ExpectedResult`, passes NUnit.Analyzers without a diagnostic. `[TestCaseSource]` methods are not inspected by either rule at all, so `TestCaseData.Returns` with `Task<TResult>` is never reported. This rule closes both gaps by rejecting `Task<TResult>` regardless of whether an expected result is specified.

## Bad

```csharp
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [TestCase(1, ExpectedResult = 2)]   // UTF1002 (not reported by NUnit.Analyzers); freezes the Editor
    public async Task<int> Increment(int value)
    {
        await Task.Yield();
        return value + 1;
    }

    private static readonly TestCaseData[] s_cases =
    {
        new TestCaseData(1).Returns(2),
    };

    [TestCaseSource(nameof(s_cases))]   // UTF1002 (not reported by NUnit.Analyzers); freezes the Editor
    public async Task<int> IncrementWithSource(int value)
    {
        await Task.Yield();
        return value + 1;
    }

    [Test]   // UTF1002 (also NUnit1013); not runnable, fails at load time
    public async Task<int> ReturnsValue()
    {
        await Task.Yield();
        return 1;
    }
}
```

## Good

```csharp
using System.Threading.Tasks;
using NUnit.Framework;

public class MyTest
{
    [TestCase(1, 2)]
    public async Task Increment(int value, int expected)
    {
        await Task.Yield();
        Assert.That(value + 1, Is.EqualTo(expected));
    }

    private static readonly object[] s_cases =
    {
        new object[] { 1, 2 },
    };

    [TestCaseSource(nameof(s_cases))]
    public async Task IncrementWithSource(int value, int expected)
    {
        await Task.Yield();
        Assert.That(value + 1, Is.EqualTo(expected));
    }

    [TestCase(1, ExpectedResult = 2)]
    public int IncrementSync(int value)
    {
        return value + 1;
    }
}
```

## Notes

- The rule matches any method marked with `TestAttribute`, `TestCaseAttribute`, or `TestCaseSourceAttribute` whose return type is `Task<TResult>` for any `TResult`. The diagnostic is reported once per method, at the return type, regardless of how many test attributes are applied to the method.
- Only `TestAttribute`, `TestCaseAttribute`, and `TestCaseSourceAttribute` themselves are matched; attributes derived from them are not detected.
- Whether the method has the `async` modifier, and whether `ExpectedResult` is specified, do not affect the diagnostic; Unity Test Framework routes by return type only.
- `ExpectedResult` on a non-generic `async Task` method is out of scope. NUnit marks such a method as not runnable at load time and NUnit1014 reports it, so it fails without freezing.
- `ExpectedResult` on synchronous methods and on coroutine-style test methods is out of scope (see UTF1001 for the latter).
- `ValueTask<TResult>` and other awaitable types are out of scope because Unity Test Framework does not support them as test return types at all.

To change the severity, add the following to `.editorconfig` or `.globalconfig`:

```editorconfig
dotnet_diagnostic.UTF1002.severity = warning
```
